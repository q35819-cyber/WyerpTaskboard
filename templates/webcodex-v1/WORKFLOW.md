# WORKFLOW.md — WebCodex 六步开发流程

本文件是唯一流程标准；其他提示词引用本文件，不重复维护状态规则。

**统一最小开发硬约束**：所有开发者先读取并实际执行项目内 `.agents/skills/ponytail/SKILL.md`（full）；先搜索原模块及调用方 → 复用现成代码/标准库 → 只做最小完整修改 → 检查 diff/必要回归；不添加需求外扩展、额外抽象、无用依赖和平台。总控派工需拒绝过度设计，独测检查 Ponytail 是否落实，不能用少代码逃避已知错误。

## 1. 派发
总控创建任务，填写目标、允许/禁止修改范围、依赖、验收条件、测试命令、开发者、独测者和目标主分支。关键条件缺失不得开工。

## 2. 开发与自测
开发者认领任务，记录 Session、分支/工作区和起始 SHA。只修改任务范围。完成后运行指定自测。
自测证据包含：提交 SHA、命令、退出码、结果摘要、报告位置。任何代码变更都会使旧 SHA 的自测证据失效。
**强制最小步骤断点**：开始开发前实际读取最新角色规范、任务主计划、历史、失败报告、`data/taskboard/checkpoints/<TASK-ID>.md` 并与 Git/Job/Session 核对；每完成一个独立可验证的小功能立刻保存代码、记录专项自测与修改清单、更新断点并登记 checkpoint_saved，核验成功后才能开始下一个；异常、换窗口、Job 阻断同理。详细规则统一引用当前项目根目录 `开发AI.md`，不能等项目最后才一次性写断点。

## 3. 独立测试
独测者必须不同于开发者。核对候选 SHA，独立取得该版本并执行验收。
报告包含：被测 SHA、实际命令、退出码、PASS/FAIL、失败复现步骤。不得复制开发者自测结果。

**独测范围裁定**：验收以用户目标和派工时既定条款为准。独测 FAIL 要附真实复现及违反的条款；已约定的功能、兼容、数据/安全缺陷必须最小修复。独测发现超范围功能、想象场景或不确定风险，只记录并申请总控在原任务计划/事件中裁定“必须修 / 误报 / 新需求另议”，不得直接升级为开发任务或无限叠加测试。开发先核对范围再修，不能无条件执行独测的所有建议；总控应主动解释裁定给两方，不能忽略已证实的真实缺陷。

**各角色阶段完成立即续接**：先核对 handoff/test-result/complete 及占用释放，再运行 `taskctl projects`、对所有项目 `taskctl list --project PROJECT` 查询实时队列。总控继续合法派工，不代领；开发优先本人绑定的交付/FAIL、其次未占用待开发；独测只接正式待独测/待复测。开发/独测对候选核验 get/history/guard、计划、报告和远端SHA，preclaim-report 后以真实 actor/Session claim 一项并直接执行，循环至无候选。不得只汇报不接、同一角色并占两个任务、后台自动唤醒或绕过STOP/HOLD/依赖。

**阻断任务必须分流**：总控每次查 `阻断`、HOLD、长期待交付/交付中及失败事件；真实功能/CLI/服务Bug派原开发最小修，证据或SHA不符回原开发重新合法交独测，测试环境问题由责任人恢复，旧设备历史身份/证据缺失由总控核查合法恢复或用户授权接管（不得伪造）。每个阻断在原任务记录原因、下一角色、动作和解除条件，不能忽略或反复建重复任务。

**分支/worktree清理归原开发**：独测PASS→原开发合并推送→合并后回归PASS→正式taskctl complete关闭→检查已合并、干净、无运行Job/其它AI占用→安全移除本任务独立worktree、删除已合并本地任务分支（禁止强制删除）；远端任务分支仅在无未关闭PR/共享引用时受控删。记录实际清理或保全原因及退出码后继续下个开发任务。总控只负责历史残留盘点和合法派工；独测不清理。不能借“清理”删除未合并/他人正在使用的工作区。

## 4. 失败回流 / 通过交付
FAIL：退回原开发者，保留报告和分支；修复后回到第 2 步。
PASS：有真实Git交付动作时进入“待交付”，保留原开发者的actor-id和Session作为认领约束，并生成合并待办；只有原开发者在原Session中可以认领。无需交付动作时由系统依 acceptanceScope 决定：system 自动完成，user_ui_business 进入待用户验收；用户不得替系统验收技术门禁。

## 5. 合并与推送
原开发者负责：同步最新远端主分支；合并通过独测的候选 SHA；冲突解决后运行必要测试；推送远端；验证远端主分支包含实际合并提交。
若合并改变候选代码，必须重新自测和独测。
合并失败：保留分支、提交和现场。调用taskctl delivery-failed记录failure-stage、failure-code、原因和下一动作；任务保留“交付中”及原开发者占用，当前进度必须展示阻断信息，由原开发者在原Session继续处理。taskctl complete核验失败时CLI自动登记同类失败事件。

## 6. 合并后回归与关闭
对远端主分支实际 SHA 执行回归。只有远端包含合并提交、回归通过且版本记录更新，原开发者以原actor-id/Session执行taskctl complete后，才关闭任务并释放占用；核验失败会自动记录阻断原因。

## 唯一状态路径
待计划 → 待认领 → 开发中 → 待独测 → 独测中 → 测试失败待修复（失败）/待交付（PASS且有真实交付）/待用户验收（user_ui_business且无需交付）/已完成（system且无需交付）→ 交付中 → 已完成或待用户验收。
`待用户验收` 只能由独测 PASS 或合并后回归核验通过后进入；通用 PATCH、AI/Bearer 身份不得代替浏览器正式用户验收。
每个任务任一时刻只有一个当前执行者和一个下一动作。待交付候选绑定原开发actor-id/Session；交付失败事件不得释放该占用。状态变更必须有看板事件，不能只改文字绕过门禁。

**24小时常设异常接管授权**：任何有待办的开发/独测/交付/阻断任务超过24小时没有真实进展，或已合并分支/worktree超过24小时未清理，允许对应角色新窗口用全新actor/Session正式接管。计时以有效状态、真实测试/代码或可信Git合并/关闭为准，查询和心跳不刷新。记录原/新身份、候选SHA、工作区、代次、原资源，防旧Session抢回；无需再问用户，**不等于可以绕过现有API或伪造用户Session**，缺能力由开发最小补足。已完成只接管遗留清理，不重开业务，禁止强删/自动唤醒。

## 异常接管
用户明确要求接管时必须执行，不得以原 AI 未登记失联为由拒绝。记录用户原话、原/新执行者、原/新 Session、任务版本和工作区证据。
不删除原工作区或未提交修改。旧 Session 恢复后不得覆盖接管后的新版本；写入前核对任务版本/接管代次。

## 上下文切换
断点至少包含：任务 ID、状态、负责人、分支、起始/候选 SHA、自测/独测报告、未解决问题、下一动作。新 Session 先读断点和 Git 状态再继续。
