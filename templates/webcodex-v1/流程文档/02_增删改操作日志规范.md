# 所有软件通用：增删改与操作日志规范

**生效流程版本：`2026.11.02-r1`。** 本规则与 `00_流程与重大更新日志.md` 一起随所有项目模板分发。总控监督；开发实现与记录；独测验证真实落盘与异常；用户不承担日志录入和技术排错。

## 1. 日志只能写在对应软件项目内部

- 每个软件按**自己的项目根目录**存日志；默认 `logs/`，例如 `logs/operations/YYYY-MM-DD.jsonl`、`logs/changes/YYYY-MM-DD.jsonl`、`logs/errors/YYYY-MM-DD.jsonl`；**不得跨项目集中在 WyerpTaskboard**。已有项目如任务看板采用 `data/logs/`、`data/events/`、`data/runtime/system-events/` 等已存在目录，优先复用，规则表明确真实目录即可，禁止为统一名称迁移或覆盖历史数据。
- 日志目录的**相对路径**必须在项目的 AGENTS/配置中写清楚；持久化采用日期滚动的 JSONL（每行完整 JSON），编码 UTF-8，追加写入，不随代码发布删除历史文件。日志属于运行数据，按项目策略备份/保留，Git 默认不提交真实业务日志；日志目录仍应位于软件项目之下。
- **代码/文件变更日志**：每次 AI 或程序对源码、配置、模板、脚本、数据库结构等**创建 / 修改 / 删除 / 重命名 / 移动 / 覆盖 / 批量编辑**均按实际动作落盘到本项目 `logs/changes/`（已有等价日志可复用）。Git 提交历史、任务事件是辅助证据，**不能替代本地操作日志**。本次每个动作至少有路径、时间、actor/Session、任务号、变更类型、变更前后 SHA256 或不存在标记、结果、Git 提交及回退引用（已知时）。
- **运行时 CRUD 日志**：软件对实体/文件/配置/数据库记录执行新增、修改、删除（包括 API、批量导入、自动化脚本、后台 Job、失败操作）必须通过本程序**已有公共写入入口**或其事务层写 `logs/operations/` 等价日志；不依赖 AI 手工事后补写。只读查询原则上无需每条记，但关键管理访问按业务需求记录。
- **错误日志**：失败的增删改也必须记录 `FAIL/BLOCK`、错误码、模块、相关操作号与重试条件；保留成功和失败的对应 `operation_id`，**不得将记录缺失的执行宣称成功**。关键不可恢复写入必须做到审计日志能可靠写入（最好与业务事务同提交，或经现有 outbox/操作事件原子保存）；审计写入失败时按项目事务边界阻止提交或明确阻断并保留恢复记录，不要以吞异常/静默降级绕过审计。日志本身的轮转/保留清理不能递归生成无限增删改日志。
- **迁移已有软件**：已有统一任务事件/操作日志、应用错误日志的，先复用并明确映射；缺少 CRUD 操作字段时由开发在对应项目的正式任务中最小补齐，并由独测验证，不能声称所有旧操作已被追溯补写。

## 2. 每条增删改日志的最低字段（相对路径 + 结构化）

```json
{"timestamp":"2026-11-02T12:00:00.000Z","operation_id":"example-001","project_id":"example-app","task_id":"EX-001","actor_type":"developer_ai","actor_id":"example-actor","session_id":"example-session","module":"project-settings","action":"update","target":"config/settings.json","result":"PASS","before_sha256":"sha256-or-null","after_sha256":"sha256-or-null","git_sha":null,"error_code":null,"trace_id":"example-trace"}
```

以上为**字段示例，不是实际发生的业务日志**。运行时数据库操作用实体类型及记录ID的非敏感替代值，不要原样记录整行数据库、用户私人信息或请求正文；批量操作记录批次/条数/失败条数，必要时保留每项索引供定位。

严禁在日志中输出明文密码、Cookie、Bearer、token、API Key、数据库连接密钥、私钥、用户隐私数据；错误栈、URL 查询参数、操作对象内容也要按键名和具体格式脱敏。日志目录应仅允许本机有权限的执行用户访问，默认本地存储，不自动上传第三方平台。

## 3. 强制执行顺序与验收

1. **每次启动**：AI先读 `00_流程与重大更新日志.md` → 校验角色版本 → 读统一入口/角色文件/任务历史断点 → 再做业务。
2. **每次写入**：确认项目根、任务权限与写入范围 → 写入前准备日志/操作ID → 执行单次增删改 → 同一业务边界落盘 PASS 或 FAIL/BLOCK → 读回校验，日志与实际代码、文件、数据库版本对应 → 保存任务断点。
3. **任何重大变更**（影响规则/流程/API/部署/数据格式等）：除该程序自身 `changes` 日志之外，还必须追加记录到 `00_流程与重大更新日志.md`，提高版本并同步影响到的全部角色入口与模板；记录“仅文档/代码候选/独测PASS/已上线”的真实状态，避免其它AI继续旧版本。
4. **总控验收**：确认各程序日志目录路径、缺失/重复写入行为、服务运行状态，并优先安排开发/独测任务；**独测验收**：真实触发创建、修改、删除、失败/重试，核对每条都能在所属程序目录检索、字段完整可关联，检查脱敏、跨项目不串日志、重启后可查询、不会重写历史。日志缺失必须 FAIL 退开发。
5. **禁止**只记录聊天、只记录 Git commit、集中一个全局日志文件代替软件日志、发生操作后不记失败、报告“已支持”但没有代码路径/实测；本规则只规定强制行为，不授权一个 AI 突然改所有其他项目的代码。
