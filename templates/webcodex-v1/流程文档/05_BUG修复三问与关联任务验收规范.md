# BUG修复三问与关联任务验收规范

**适用范围**：所有接入任务看板的软件项目、所有 `bugfix` 任务，以及任务执行中发现的独立BUG。由开发 AI、唯一独测 AI、总控 AI 按自身真实阶段分别执行；不改变已有三轮自测、独测和总控交付职责。

## 一、每次修复后必须完整回答（回答模板）

1. **问题解决了没有？** 结论只能为「已解决 / 部分解决 / 未解决 / 无法确认」，写明原故障、受影响范围、修复文件或候选SHA、实际验证步骤/退出码/结果。开发只可确认候选自测；独测只可确认独立测试；只有总控在部署及真实流程回归后可确认生产问题解决。
2. **下次会不会复现同样的问题？** 不能保证绝对永不复现。写明相同根因及触发条件是否已被排除、用于证明的复现用例和反向/回归测试，以及未覆盖的触发条件和残余风险；结论用「已验证原复现路径不再触发 / 仍可能复现 / 无法确认」，不得凭一次PASS推断所有场景。
3. **后续流程是否正常？** 从故障发生点实际测试并说明下一角色/任务的合法准入、状态转换、交接、续接、独测、合并/运行是否通畅；列出真实任务状态、事件ID、下一步和测试结果。没有跑完下游就写「部分正常 / 尚未验证」，不得只因该BUG单测PASS就写「全部正常」。

每个答案**必须包含结论、范围、实际证据与尚未验证项**；禁止空白、只写PASS、只有流程口号或复制上一轮答案。输出位置：执行角色的聊天汇报 + 对应任务自测/独测/交付报告或正式事件可追溯位置。任何角色不得冒认其他角色的测试与发布结果。

## 二、有关联任务或当前无法准确回答

- 若三问中的任一项还不能下结论，必须明确「无法确认/部分解决」并列出**每一个直接关联的正式任务编号、状态、负责角色、剩余条件和复核触发点**；同时说明哪些证据已经通过、哪些尚未执行。不得隐去阻断、仅写「等待修复」或伪造已完成。
- 同一故障跨多个小任务修复时，**允许等关联任务全部合法完成后，由最后的责任角色对整体故障只提交一次最终三问完整报告**；各阶段仍需在自己的报告中留下当前三问状态和关联编号，不能省略。关联任务未全部完成前，单项代码可以按其独立范围走原有合法交付，但必须写明「仅本项完成，整体BUG尚未闭环」，不能宣布整个故障修复完成。
- 已完成任务不追加新需求、不扩写其任务范围；新发现的独立BUG建新的最小任务并与原编号互相关联，不为这份三问规则重开已完成历史任务。

## 三、角色强制出口与完成判定

- **开发 D08**：三轮自测PASS后回答三问，注明「仅开发候选」及关联任务ID，写进自测/交接材料，再正式交唯一独测；缺一问或凭空称运行已正常，视为交接资料不完整，必须补齐，不得写「BUG全部修好」。
- **独测 Q03**：独立复现原BUG、验证修复及相关负向和下游入口，重新回答三问；FAIL返回原开发，PASS也不能代总控宣称已发布。无法验证下游时标「尚未验证」并给关联任务。
- **总控 C07**：在正式独测PASS、合并、运行版本和最新主线回归后再次回答三问；**三问齐全且有对应事实依据才允许判定整体BUG修复完成**。有关联任务未关闭时可完成经独测的独立小任务，但必须保留整体BUG未闭环和关联编号；待关联任务真正完成再合并作一次最终回答，不得自动把其它任务改为已完成。
- **完成硬判断（规则层面）**：缺任一问题、缺证据、存在未知结论却无关联任务编号，均为「BUG修复结论未完成」，不得向用户宣布整体修复成功。不能为通过三问而绕过TaskStore真实状态门禁、创建虚假PASS或修改已完成任务。

**部署边界**：此文件是统一权威流程规则，须同步 `templates/webcodex-v1/流程文档/`。本规则的角色汇报和报告要求在文档层执行；服务端目前未实现对“三问文本”的自动识别/阻止关单，**不得将文档更新说成程序硬校验已上线**。如需服务端自动识别，应独立建小任务开发并经正常独测交付，不扩展任何已完成任务。
