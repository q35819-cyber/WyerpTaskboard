# 所有软件：三段版本号、需求先记录再派工

**适用版本：`2026.11.02-r3`。** 这是全软件通用开发规范，与角色及 Git 交付门禁共同生效；版本号表示**已正式交付的软件发行版本**，不是任务编号、规则版本或未合并候选数。

## 软件版本号统一规则

固定 `主版本.次版本.修订号` 三个非负整数，示例 `0.0.0`，禁止用日期/任意字符串替代正式版本号。

- **主版本（第一位）**：重大功能或不兼容大变更：第一位 +1，**后两位都归零**，例如 `0.6.63→1.0.0`、`1.8.25→2.0.0`。
- **次版本（第二位）**：普通兼容功能：第二位 +1，**第三位归零**，例如 `0.6.63→0.7.0`、`1.8.25→1.9.0`。
- **修订号（第三位）**：BUG修复/补丁：第三位 +1，前两位不变，例如 `0.6.63→0.6.64`、`1.8.25→1.8.26`。
- 开发应在送独测的候选中按已批准的发布级别修改版本文件，独测核对；**只有**总控受控合并、回归及软件主目录真正发布成功后，才能把候选版本确认成已发布。仅需求或文档变化、未合并候选不冒称已发布。一次发行包含多种变更时，按影响**最高级别**确定一次版本提升，避免一个任务反复叠号。
- 总控先记录准备发布的变更级别与选择理由，开发维护实际版本文件，独测核对候选版本和兼容性，总控交付时核对远端main/本地主目录/可核验运行版本及版本日志。若版本异常，先记录并处理，不猜测版本。

## 所有需求讨论先记录（再讨论、再派工）

1. 用户提出需求、建议、错误反馈、规则调整或重大设想时，先在**该软件项目自己的需求池**登记一个需求编号（可使用现有 `data/requirements/` / 任务看板需求存储；没有时用项目根 `docs/需求记录/` Markdown），不以聊天记录代替。记录时间、原话/目标、所属项目、影响模块、优先级初判、讨论问题、用户决定、验收范围、当前状态、关联任务号与证据。
2. **有疑问先把问题和讨论结果追加到同一需求记录**。用户已明确的部分直接记录不重复追问；禁止未明确就擅自扩展功能。以用户最终确认的决定为准，保留修改历史，不覆盖旧要求。
3. 讨论记录可以先连续积累，尤其是需求很多时：标记 `待讨论` / `待整理` / `已确认待派工` / `已派工` / `已完成` / `不采用`，定期根据优先级、依赖和文件占用**合并去重、分批正式建任务**。**不要求用户一次讨论完就立即创建大量任务**，但不能漏记或把未确认当成已批准。
4. 派工前从需求池核实目标、验收条件、约束、前置、角色责任与真实状态/文件冲突；正式任务记录必须反向引用需求编号，需求记录必须回写任务编号与执行状态。需求多时先完成登记，再挑选具备条件的最小批次；绝不能一边讨论一边在无记录的情况下随意派工。
5. 重大决定如影响流程、版本、API、部署、数据或多项目，除需求池外还必须同步写 `00_流程与重大更新日志.md`；每次增删改和失败按 `02_增删改操作日志规范.md` 留在所属软件根目录。总控收到需求先按C00_A登记，正式开工前再执行C00_B版本核验及C00_C快速清理检查，然后派可执行开发/独测队列，随后继续自己的技术交付。

**不得混淆**：本日志的 `2026.11.02-r3` 是流程规则版本；软件的 `0.0.0` 是独立的产品版本。
