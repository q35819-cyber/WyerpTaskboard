# WTB-P1-DELIVERY-TASK-RECOVERY-20261031-T1

本任务遵守产品级基线 `docs/产品需求/00_WyerpTaskboard核心产品需求.md`：只有总控、开发、独立测试三个常设角色；任务编号是新窗口唯一执行入口；Git 同步、合并和远端核验不得要求用户手动操作。

## 目标

建立“任务编号即执行入口”的可靠机制。用户只需把一个任务编号发给新窗口或指定的开发/独立测试窗口，该窗口就能从 WyerpTaskboard 读取完整、最新、可执行的任务上下文，不依赖旧聊天记录，不要求用户重复粘贴长提示词。

任务创建和角色分配由 WyerpTaskboard 总控 AI 负责；开发 AI、独立测试 AI 不得给自己创建或分配任务。开发完成后按同一任务编号交给独立测试 AI，失败回到原开发 AI，PASS 后按既有交付规则闭环。

## 用户已经明确的使用方式

1. 总控 AI 在 WyerpTaskboard 创建正式任务，补齐计划、范围、依赖、角色和验收标准。
2. 总控 AI 决定分配给开发 AI 或独立测试 AI，并维护任务当前状态和下一责任角色。
3. 用户把任务编号手动发给对应的新窗口/开发窗口/独立测试窗口。
4. 收到编号的窗口必须先按编号查询任务看板，自动读取完整任务计划和必读材料，再决定当前是否有权执行。
5. 用户不需要再解释任务内容，也不需要把计划文件、测试要求和历史记录逐一复制到新窗口。
6. 编号不存在、重复、任务资料缺失或当前角色/阶段不匹配时，窗口必须明确报告阻断原因，不得猜测任务内容、擅自创建任务或越权执行。

## 三个常设角色与权限

只保留三个常设角色：**总控 AI、开发 AI、独立测试 AI**。不得新增规划 AI、集成开发 AI 等第四角色；需求拆分、创建、派发和任务恢复由总控 AI 承担。

### 总控 AI

- 唯一负责创建正式任务、确定任务编号、父任务、优先级、依赖、计划文件、读写范围、验收标准和计划角色。
- 负责把任务分配给开发 AI 或独立测试 AI，并根据任务状态决定下一责任角色。
- 负责检查异常、缺失任务、未完成依赖和失联执行者；用户要求异常接管时按受控接管规则处理。
- 创建和分配必须留下可审计的 actor、Session、时间、任务版本和历史事件。

### 开发 AI

- 收到任务编号后，先读取完整任务上下文；只执行当前状态允许的开发/修复/交付阶段。
- 只能认领总控已创建且当前角色为开发 AI 的任务。
- 不得调用创建任务接口给自己派任务，不得自行改变计划角色或给自己分配其他任务。
- 完成开发自测后，按原子交接流程交给独立测试 AI；独测 PASS 后由原开发 AI 负责必要的合并、推送、远端核验、合并后回归和关闭。

### 独立测试 AI

- 收到同一个任务编号后，读取同一份最新任务上下文、开发自测报告和固定候选 SHA。
- 必须使用与开发 AI 不同的 actor-id 和 Session；只执行独立测试/复测阶段。
- 不得创建任务、分配任务、修改业务实现或代替开发合并。
- FAIL 自动回到原开发 AI；PASS 按任务交付模式进入待交付、待用户验收或系统自动关闭。

## 任务编号查询与完整执行上下文

**P1子任务开发基线并无 `context` 子命令；本隔离开发候选新增 `context --task` CLI/API，只有经真实功能自测、独立QA与合并交付后才可称部署可用，不能将开发分支命令当作现网服务已经实现**。统一入口命令：

```powershell
node cli/taskctl.mjs context --task WTB-P1-DELIVERY-TASK-RECOVERY-20261031-T1
```

要求：

1. 默认只提供 `--task` 即可；服务在全部已登记项目中精确查找任务编号，不静默默认到某个项目。保留显式 `--project` 的限定查询能力。
2. 该入口必须能从任意已接入项目的新窗口调用，不能要求开发窗口先切换到 WyerpTaskboard 仓库目录；可通过现有 WebCodex/任务看板连接器、统一 CLI 入口或等效受控 API 提供，内部再安全访问任务看板服务。
3. 全部项目中唯一命中时，返回项目 ID/名称、任务完整记录、当前状态、计划角色、负责人/Session、父任务、优先级、任务边界、溯源、只读依赖、写入范围、目标位置、验收范围、结构化前置任务和当前下一动作。
4. 同时读取主计划和所有关联计划/文档正文，并附上最近任务历史、开发自测/独立测试/交付报告路径与 SHA 证据、候选分支/SHA、当前阻断项和当前可执行角色。
5. 输出应是新窗口可以直接执行的完整任务上下文；不能只给文件路径，也不能依赖当前聊天历史。
6. 任务编号全项目唯一命中：正常返回；没有命中：返回 `TASK_NOT_FOUND`；多个项目命中相同编号：返回 `TASK_ID_AMBIGUOUS` 并列出冲突项目，禁止任意选择。
7. 主计划或必读材料不存在、超出读取限制、路径不安全或内容无法读取时，明确列出缺失材料和阻断原因；不得声称已经读取，也不得静默跳过关键规则。
8. 不在上下文包中暴露 Bearer、密钥、Cookie、私人配置等敏感信息。
9. 可保留 `get --project PROJECT --task ID` 作为精确查询兼容命令；新窗口入口必须支持仅凭任务编号完成查询。

1. 创建任务必须由经服务端验证的总控身份发起。不得仅相信请求正文中的 `actorType=controller_ai`、`actorId` 或命令行参数，避免开发 AI 伪造总控身份。
2. 服务端必须拒绝 `developer_ai`、`test_ai` 直接创建正式任务；拒绝结果不产生任务行、创建事件或部分副作用。
3. 总控创建时必须校验任务编号唯一、计划文件存在、角色与初始状态匹配、写入范围非空、验收条件和测试要求完整、依赖有效。
4. 总控创建后，任务默认只设置下一责任角色，不得在创建时伪造开发者/Session 的正式 claim；实际执行仍需对应 AI 使用自己的身份正式认领。
5. 新窗口只能按任务当前状态和 `plannedRole` 执行：开发窗口不能冒充独测，独测窗口不能继续开发；角色不匹配时返回明确错误和应由谁执行。
6. 当用户手动提供编号但查询不到时，开发/独测窗口只报告 `TASK_NOT_FOUND` 并交回总控；不能自行创建同编号或相似任务。

## 总控“继续”增量恢复与 Git 成果对账——新必需验收

- **总控第一步**：从主仓库最新总控断点读取各开发/独测窗口分别绑定的任务ID及已派发未完成任务集合、核验过的 event ID / registry revision、candidate SHA、报告 SHA256、远端 main SHA、原 actor/Session、当前阶段与唯一下一动作；先读断点再使用 taskctl get/history/guard。仅检查上次派工**之后新增的事件或变化的 SHA**，已验证且未变的阶段必须跳过重新测试。缺断点/事件无效才回退全量审计。
- 同一用户连续多次说“继续”、状态和候选均未变时，不得重复认领、重复提交 npm test Job、重复派工、重复写同一结论的事件。状态改变时增量核验新门禁并记录新的断点；失败及时回原责任开发，不让用户手动判断技术故障。
- 每次总控回复**先给每个已运行开发AI及唯一QA的流程状态，再按各合法空闲窗口明确下一任务编号、角色、阶段及需要时的唤醒语句**；多个可并行的开发AI可以分别有下一任务，单个AI仍仅有一个当前任务，不把任务已派发说成执行完成；用户只负责唤醒 AI，技术协作和状态闭环由系统完成。
- **Git 可交付成果持续对账**：任务和工作区注册表中持久维护任务 ID、worktree 路径、HEAD/dirty/untracked/ignored 数据、候选分支/SHA、与远端 main/候选 ahead-behind、独测与回归证据、任务归属、处置类别、清理条件；Git 标记干净仍须检测 ignored 文件/旧运行产物。
- 自动分流三类：①已独测 PASS 但未合并，必须在原任务内生成待交付阶段待办（不是新建重复任务），由原开发执行 merge/push/远端核验/回归；②未提交有价值成果，锁定归属、保留断点和 dirty 文件，完成原任务流程再合并；③已合并且确无任务占用、无未归档唯一文件/忽略数据的旧工作区或分支，**先形成只读清理候选清单**；由用户已手动唤醒、正式有权的开发AI在当前交付/维护阶段执行逐SHA归档校验与安全清理并登记事件，严禁状态变更后无人值守自动删除工作区或远端分支。
- **合并之后**，重新核对每个工作区与真实远端主分支的版本；旧工作区该保留的继续隔离开发、该归档的先存 SHA 清单和文件；不能仅 `git reset --hard`、强推或删除用户私人资料来伪造 Git 一致。最终关闭任务时需证实所有任务范围内代码已包含在远端，或已明确登记为拒绝/归档/等待交付的例外，不允许无限期保留无人处理的本地修改。
- 具体验收包含：重复“继续”两次只核验一次且无重复测试；上次事件后新独测 PASS 正确转交原开发；独测 FAIL 正确回流；候选 SHA 改变强制重新验证；一个有 dirty 文件的工作区被保护；一个 Git 干净但含 ignored 日志/计划的旧工作区先归档再移除；远端 main 变化时阻止过期合并；任务正式完成时最新远端 SHA、回归和看板状态一致。
- **阶段与 Git 范围**：该能力属于既有 P1 正式任务，完成两个 P0 前置门禁前仍 HOLD；根目录 `总控AI.md` 规范及自动检测/清理代码必须在本 P1 的受控任务分支内版本化、开发自测、独测、推送合并。当前先以总控运行时断点和人工增量检查执行，不能把规则修改或本地文件当作代码已交付。



### 总控监督所有开发AI与唯一独测AI，先报审计结果（用户2026-11-01新要求）

用户不再亲自催促或分别检查各个开发AI和独测AI；**总控每轮必须先输出所核验的开发/独测/交付流程及其结论，才输出进度和下一角色**。以根目录`总控AI.md`最新“每次先审流程再汇报”为规则来源，本P1内核应提供可机器读取的阶段证据投影：taskId、status、责任actor/Session、每阶段最新preclaim/claim/test-start/test-result/handoff、断点eventId、候选/远端main SHA、报告哈希、运行Job、前置/资源/越界门禁、是否已经完整核验；在无证据时明确“未核验/进行中/未到阶段”，禁止使用状态字符串伪造PASS。

**强制验收场景**：1）开发仅发口头“完成”无正式test_result→开发流程异常；2）开发和QA actor/Session相同→独测拒收；3）候选SHA与被测SHA或报告hash不符→阻断；4）独测中有合法claim/test-start、无test_result→流程目前正常/结果进行中；5）独测FAIL→同一task ID退原开发；6）独测PASS→提示用户手动唤醒原开发Git交付，不能自动合并；7）交付已push但缺合并后回归/关闭事件→只报待交付/交付中；8）“继续”前后业务事件水位不变→复用断点、无重复测试/消息/事件；9）服务重启或执行Job仍未完成→只报待核验，不能冒充终态。该能力的实现、独测与远端合并必须在本P1任务合法解除HOLD后实施；当前本地修改规则不等于软件功能已交付。

### 真实并行开发、唯一独测队列与用户异常接管（2026-11-01补充验收）

- **并行下Git关口**：A/B可独立待交付，但受控合并main必须串行；后交付者核对最新远端main、独测SHA及代码/资源影响，变更候选或需重定基时不能沿用旧PASS，必要时重新开发自测、独测。防双写锁的判断包含路径父子、通配、实际修改集、共享契约及不可隔离资源。

- **开发接管区分阶段**：开发中/修复中接管后继续修复并按新候选完成新的开发自测/独测；待交付/交付中先验证原独测报告非空、证据HASH/commitSHA绑定真实Git再交付；缺失就回独测，用户接管授权不等于独测豁免。**QA独测中断时也允许用户明确命令新的独测AI合法接管**，旧QA立刻失权，统一队列仍只一个QA;旧测试运行日志可用于诊断而不直接冒名继承未完成PASS。

1. **五类对象分离**：任务 Task（稳定 ID/项目/依赖/验收范围）；阶段 Stage（现有兼容状态机）；执行者 Assignment（角色、actor-id、Session、工作区）；执行 Attempt（job、候选 SHA、开始/终止结果）；不可篡改 Event（每次决策/失败/交接与证据）。同一任务可有多次 Attempt，但不得让旧 PASS 自动继承到新 SHA。
2. **任务状态与执行状态分开**：保留已部署的 `开发中/待独测/独测中/待交付/交付中/已完成/HOLD` 等兼容业务状态；另提供 `未唤醒/已指派待人工唤醒/已认领/执行中/阻断/异常待接管/已交接` 等只读派工/运行态投影，基于真实 Session、事件、Job 计算，绝不把“派发消息已送达”假报为“AI 已开始”。状态迁移不得凭任务卡文本推断。
3. **三角色可信边界**：常设总控、开发、独立测试三个角色；任务创建/分配仅经服务端可信总控身份授权；独测必须不同 actor-id 和 Session、独立取远端 SHA；开发不得给自己创建任务/伪造独测；交付必须原开发或用户明确授权接管的开发。拒绝仅凭 HTTP body 声明角色就越权通过。
4. **人工唤醒门禁**：开发自测 PASS 后系统原子记录待独测交接，页面显示应唤醒“独立测试AI”；正式 claim 和用户实际唤醒前不得启动 Job。独测 FAIL 仅在**同一任务ID**上原子记录失败证据、修复状态与原开发 actor，不自动新建修复任务或唤醒开发；PASS 仅登记待交付，由用户手动唤醒原开发。若 Session 失联/重启，只提示受控恢复，未经用户明示接管不能自动更换 actor、窗口或文件所有权。
5. **完整上下文入口**：只提交任务编号，新窗口从服务端读取任务当前 state、主/关联计划全文、根目录三角色规则、最新失败与断点、测试报告、候选 SHA、当前 Job、可执行工作区、待处理文件差异、下一动作；拒绝缺资料/重复编号/过期断点。其他软件不需要复制 WyerpTaskboard 根路径。
6. **增量“继续”防重**：总控断点持久化最后核验 event ID/registryRevision、阶段、候选 SHA、远端主分支 SHA、报告 SHA256 和最后实际 Job；重复收到“继续”而关键水位未变时，不能重新跑同一测试、重复认领、重复派工或重建 worktree；仅核查新增**业务推进/测试/交付**事件、变更证据、过期风险；总控自身无变化的查询、checkpoint_saved、重复消息不能作为触发下一轮重新核验或重复写入的业务事件。关键水位不变时不产生重复checkpoint_saved、派工、Job或新任务；新 SHA 必须重新自测/独测。服务端提供可查询的增量事件窗口和幂等操作键。
7. **小功能级原子断点**：读文档/计划和 Git 首检后才准 claim；每完成最小功能即记录 stepId、修改集、SHA、Session/Job、实际检查退出码和唯一下一动作；断点写入与 `checkpoint_saved` 事件要做到可恢复/幂等（含文件落盘与事件登记半完成的故障注入），断点丢失不能跳至下一步。
8. **危险行为权限模型**：清理未提交成果、删除远端分支、强推、覆盖项目文件等不得由仅一条自动状态迁移触发。Git 合并仍由人工唤醒的原开发执行；不允许默认自动授权，需真实版本校验、证据留存和可恢复归档，必要时才由用户明确批准不可逆操作。
9. **交付工作区治理**：把“服务端验证的干净交付 worktree / 真实远端 main”和“注册主仓库 dirty 现场”分开；如果主仓库 dirty 属其他任务，必须先做文件级归属、保全、SHA 归档/恢复核验，不得要求重做已经 PASS 的独测，也不能因为隔离工作区通过就略过全项目 Git 对账。任务关闭后清理无人占用、已合并且已归档唯一内容的 worktree/分支；原有 dirty/ignored/private 数据不能当垃圾删除。
10. **输出可核查的下一动作**：API/CLI/看板同一投影必须明确 task ID、当前责任角色、已验证与未验证门禁、所需启动指令、当前窗口 Session、最后已完成 step、缺失的证据和预计修改文件范围。下一动作若受阻必须说明原因，不用用户来判定技术故障。

### 子任务独立验收用例

- 手动唤醒开发、手动唤醒不同 Session 独测、FAIL 回流原开发、PASS 待交付、原开发手动唤醒完成 Git 全流程：状态和权限均正确、没有后台自动启动任何 Agent/Session/Job。
- 未实际启动的 Session 只显示“待唤醒”；消息已投递而未 claim 不得变成“执行中”；Job 异常中断或 Session 换窗口须展示可恢复断点而不是自动恢复。
- 连续两次“继续”且事件/SHA 不变：零重复开发、零重复测试 Job、零新的 claim；独测 SHA 发生改变后旧 PASS 必须失效。
- 连续两次仅查看相同任务、不发生业务状态变化：总控不得因为自己上一轮 checkpoint_saved 事件而反复写新的 checkpoint_saved、产生虚假的活跃度；只能返回同一待唤醒责任人与断点，不重复派消息或作出成功声明。
- 模拟独测 FAIL：只能原任务切回修复阶段并生成同一任务的下一责任人，不能自动新建修复任务、不能自动恢复原 Session；需用户下一次唤醒开发AI。
- 模拟已完成任务中无占用但存在 ignored 独有文件：状态变化本身不会自动删除，必须由合法开发AI明确进入清理步骤、逐文件SHA归档并验证后才移除。
- 开发冒充 tester 或控制端创建任务被服务端拒绝且无副作用；多任务跨项目 ID 碰撞正确阻断；请求正文伪造 `controller_ai` 不能生效。
- 远端 main 已合并、合并后回归通过，但注册主仓库 dirty：应明确识别已有已交付工作区、要求安全保全/对账并能完成合法关闭；不能 reset/删除其他任务成果。工作区已合并/无人占用/含 ignored 日志：归档逐 SHA256 校验后才可清理。
- 两个最小功能后断线，恢复不得重做第一个功能；模拟文件断点成功但事件写失败、事件成功但文件写失败，仍可恢复一致；保留原窗口 Session 与历史。
- 保留 `npm run check`、`npm test`、权限、旧 WebCodex 工作区、现有任务格式回归；完整独测绑定精确候选提交，正式报告包含真实退出码、数量、SHA/报告哈希。

**范围分配与排序**：本 P1 子任务只实现可信身份、任务编号完整上下文、任务/执行状态分离、人工唤醒交接、增量断点、Git 交付安全门禁的通用**内核与 CLI/API**。通用项目 profile、Node/Python/.NET 接入、看板展示和新项目模拟验收由父任务 `WTB-P1-UNIVERSAL-SOFTWARE-WORKFLOW-TEMPLATE-20261031-T1` 在同一内核上完成，不得重复实现一套状态机或同时并行改同一后端。用户最新确认的人工唤醒要求优先于旧计划中“自动执行/自动调度”的描述。当前两个 P0 前置任务未全部完成，保持 HOLD，**不认领/不写功能代码**；总控先按依赖依次安排。

3. `context --task <ID>` 必须一次返回最新任务记录、主计划/关联文档、最近历史、最新断点路径与更新时间、当前窗口/Session/Job、Git 现场、报告证据和下一动作。不能只返回计划路径。

### 每个小功能强制保存与开发前读文档——优先实现的硬门禁

7. **开发启动/接管/换 Session** 的统一上下文加载必须实际读取根目录及角色规范、主计划、历史、最近失败报告和最新断点；输出读取结果或缺失明细、各文件版本/摘要和 Git/Job/Session 核对结果。未完成读取或断点与实时任务/工作区冲突，服务端正式认领和执行推进应返回可验证的 `CONTEXT_NOT_VERIFIED` / `CHECKPOINT_STALE` / `CHECKPOINT_MISSING` 错误（具体错误码稳定一致即可），不能只是聊天提醒。

10. 现有任务的初始断点、旧版 Session 接管和旧工作区 dirty 文件须兼容；新窗口仅凭任务 ID 先取得**最近一个已完成小步骤**及之后可能发生但未记录的 Git/Job 变更，先核对差异再继续。
