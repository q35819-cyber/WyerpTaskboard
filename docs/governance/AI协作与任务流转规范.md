## 0. AI协助第一守则

本项目所有角色先读并遵守 `docs/governance/AI协助第一守则.md`。尤其要求：先检查前提、逻辑与缺失信息；不迎合用户并区分事实/推断/未知；关键数字和结论核实当前来源；有异议直接说明依据、影响和替代方案；主动提醒权限、并发、隐私、成本、兼容性、人工接管、误判和恢复风险；新增独立能力、跨组件功能和高风险自动化默认先建或更新计划，再实施。

该守则不替代任务状态和角色规范，而是所有状态流转与执行动作之前的首层检查。

## 1. 两类责任，不是一人包办

开发AI负责需求整理、已授权实现、修复、自测，以及**确有真实交付动作时**的本任务交付；测试AI负责未参与实现功能的独立验证、失败报告、复测，并在技术通过后记录交付必要性判定。接到新需求的AI先给独立意见，说明合理性、冲突、风险和替代方案；用户已明确执行且范围清楚时继续，不为普通步骤反复索要许可。

用户保留业务取舍、扩大授权和最终视觉/业务验收。明确“只讨论、只读、先给方案、等确认”时，不实施、不下发或恢复其它任务。**独立测试资格只以是否实际修改过被测任务代码为准。** 角色切换、重开会话、同一模型换名称不能抹去真实代码修改事实；实际修改过本任务代码的执行者不得充当该功能独立测试者。仅编写/更新测试报告、测试断点、治理规则、计划、说明文档、审计记录或其它纯文档内容，不算参与代码实现，不影响后续独测/复测资格。前后端边界仍按任务范围分别执行，取消调度不等于授权跨端改动。

测试AI可以准备已授权的测试账号和夹具、写报告与断点，并可按职责更新测试/治理类纯文档；这些文档写入不影响独立测试资格。测试AI不得修改被测任务代码、测试代码、可执行脚本或其它会改变运行行为的代码内容，不降低验收标准，不自行修复。只要本测试AI没有改过被测任务代码，就允许由同一测试AI在开发修复后继续执行复测；发现误改代码时才停止独测、说明范围，后续由未修改该代码的测试者重新验证受影响项。

**角色过滤先于任务排序**：任何AI自动扫描/候选消费都必须先按当前角色过滤任务，再在角色内比较阶段、产品阶段、轨道、优先级和阻断性。开发AI不得因为某个独测/复测任务P值更高就跟踪或接管测试执行；测试AI同理不得因为开发任务优先级更高就介入实现。失败报告作为跨角色交接输入，不等于当前角色取得对方任务执行权。

## 2. 开工与任务准入

读取AGENTS、文档索引、本文、对应角色规范、任务认领与资源占用规范、最新台账和本任务断点；再按领域读专项计划，不全文重复读取所有无关文档。

任务进入可执行队列前必须具备：唯一任务ID及父功能ID、用户已确认范围及排除项、可判定验收项、计划写文件与只读依赖、当前版本/工作区、前置依赖、风险/外部授权、报告与断点位置。测试任务还需开发交付记录、实际自测证据、固定被测版本及对应环境。

### 2.1 先建任务、后开发（硬门禁）

1. 任何新需求、Bug修复、新增测试实现或会改变运行行为的工作，在**第一次修改业务代码、测试代码、可执行脚本、迁移、配置或其它运行行为文件之前**，必须先完成：生成稳定任务ID；写入对应项目任务注册表并明确父功能、track、优先级、当前阶段、计划角色、职责边界、主计划、只读依赖、计划写文件、断点/报告入口；在当前聊天向用户汇报任务ID、主要内容、当前阶段/可认领依据和本轮边界；重新核对实时占用并成功 `claim`。
2. **禁止“先改代码、后补任务”“先写测试、后建任务”“先修一点再去认领”。** 任务候选、聊天里已经讨论过、计划正文里提到过、用户口头说“继续做”都不能替代正式任务ID和成功claim。
3. 唯一例外是紧急安全止损：为了阻止正在发生的数据损坏、凭据泄露、无限扣费、错误发布或其它高风险副作用，可以先执行最小停止/隔离动作；止损后必须立即登记正式任务。**在任务正式claim前，不得借“止损”继续做功能实现、重构或完整Bug修复。**
4. 若发现已经发生“代码先改、任务后补”，必须：立即停止继续修改 → 建立/关联正式任务 → 记录 `governance_correction`（或等价治理纠正事件）→ 如实写明真实修改时间、补登记时间和影响文件 → 再按正常claim继续。**禁止倒填、篡改或伪造提前认领时序。**
5. 纯需求分析、只读定位、计划/任务注册表本身的登记，以及为了创建正式任务所需的最小治理文档写入，不属于业务实现，可以发生在claim前；但一旦开始修改运行行为文件，就必须满足本节门禁。

### 2.2 执行中发现问题必须落任务，但禁止AI自行制造新需求（硬规则）

1. 本规则只适用于**已经存在的需求、计划、规范、验收标准、已声明行为或安全/数据完整性边界下发现的真实问题**，例如：Bug、回归、测试失败、实现遗漏、数据错误、权限越界、安全风险、治理规则违例、文档与真实实现冲突、已批准功能缺口。
2. 只要上述问题**不属于当前任务已明确边界，且不能作为当前任务内的最小安全修复直接收口**，发现者必须立即执行唯一处置之一：**关联现有任务**或**创建独立问题任务**。不得只写测试报告、断点、聊天汇报或“后续再看”而不进入任务注册表。
3. 问题任务建立后，仍必须遵守角色、优先级、claim、资源、测试和Git门禁；“发现问题必须建任务”不等于“发现者可以跨任务顺手修复”。
4. **本规则不得用于自动制造新需求。** AI自行想到的功能扩展、体验优化、重构建议、产品创意、可选增强、未来能力、非既有标准要求的“可以更好”，一律不得自动创建为正式任务、不得自动进入“待确认”、不得借“发现问题”名义写入项目注册表。
5. 新需求只有两种合法来源可以进入正常需求拆解/建任务流程：**用户已经明确提出**，或**既有已批准计划/需求已经明确包含**。除此之外，AI自行想到的优化建议、功能建议、产品想法和候选新需求，统一写入任务看板根目录 `AI优化建议与候选需求池.md`，默认状态只能为“待用户查看”；不得进入正式任务注册表、不得触发自动执行、不得由AI自行标记“已采纳”。只有用户明确采纳后，才按正常需求流程转成正式任务。
6. 判定边界：能指出“违反了哪一条已有要求/计划/测试/安全边界”的，属于问题；只能说明“这样也许更好/可以新增”的，属于建议或候选新需求，应进入 `AI优化建议与候选需求池.md`，不得自动任务化。


**开发自测时间顺序门禁**：开发中/修复中的最后一次代码变更之后，必须存在针对该变更范围的有效开发自测证据，才能进入待独测/待复测。只要代码在最近一次自测之后再次发生逻辑变化，原自测对受影响范围立即失效；开发AI必须补测后才能交接。该规则优先于“已写完代码”“全量以前通过”等口头状态。

**真实接口验证通用规则**：开发AI自测和测试AI独测/复测都允许在任务授权范围内调用真实外部接口、使用真实接口测试数据取得必要证据；“控制频率和额度”是默认约束，不得把真实接口一刀切禁用。执行者应先复用已有真实证据，再按最小样本、最少请求、低频串行方式补缺；必须遵守项目自身Key池、预算、限流、熔断和平台规则，并在报告/断点记录平台、场景、请求量或额度变化、结果。已足够证明的场景不为重复确认再次消耗额度；发现限流、额度不足、封禁风险、异常扣费或实际请求量明显偏离预估时立即停止扩大请求。涉及不可逆生产写入、真实发布/购买/收费等高副作用动作仍按专项授权执行，本规则只授权必要测试调用，不扩大业务操作权限。

缺少材料的任务为“待准备”，不得仅凭一句已开发或一个尚未创建的报告路径自动开测。对用户已授权的这类任务，计划角色可取得认领和必要文档资源后自行准备资料：只读定位已有实现、收集报告/版本/授权范围、建立本任务断点；资料齐全才切到相应就绪阶段。准备阶段不擅自修改业务代码、启动测试、重拉收费数据或重做已完成部分，无需等待专职调度。已有证据先复用，只补缺项，不能借准备任务重做已完成实现。模板路径必须注明领取时创建，不伪装成已存在证据。

**待准备的受控认领**：按已完成 WTB-QUEUE-002 的现行规则，`待准备 + plannedRole=开发AI` 可进入开发候选；只有需求范围已授权、计划写文件明确，且用户留言、stop、owner/session、依赖及资源等实时门禁全部通过，才能claim进入开发中以补齐本任务准备/证据。缺少已确认业务规则时仍不能猜测开发；claim只授权已登记范围，不能越过硬前置。资料不足回流由开发AI补齐，不把测试AI留在不可领取的待准备阶段。

**认领前先报任务、再做实时占用复核。** 所有AI在正式claim前必须先在当前聊天向用户汇报任务ID、任务主要内容、当前阶段/可认领依据和本轮边界；这一步用于让用户及时发现接错任务，默认不新增审批等待。随后必须基于最新任务快照重新检查占用：`开发中/修复中/独测中/复测中/交付中` 均属于已占用进行态，任何非空负责人或Session也视为占用；存在活动Job/资源或未闭合接管时同样不得抢占。只有明确处于当前角色可认领阶段且无任何活动占用时才允许claim。用户在claim前指出“有人在做/接错/暂停”时，立即停止并重读真值。

## 3. 唯一任务阶段表

以下为任务阶段的唯一允许值；资源排队/租约、单条用例结果、上线状态和用户验收分别记录，不拼成自由文本状态。

| 阶段 | 进入条件 | 谁记录/下一步 |
| --- | --- | --- |
| 待确认 | 范围或规则存在需要用户决定的事项 | 发现者列证据与方案，用户决定后进入待准备 |
| 待准备 | 范围可知，但交付材料、固定版本或前置条件不齐 | 开发AI按本节门禁受控认领补齐；测试证据不足也回开发，不允许未就绪独测 |
| 待开发 | 已确认需求与依赖齐全、尚无有效执行者 | 合格开发AI取得认领与资源后进入开发中 |
| 开发中 | 开发AI已获执行权，正在实现/自测 | 交付资料和自测齐全后进入待独测 |
| 待独测 | 开发交付齐全，独立测试尚未开始 | 合格测试AI成功认领后进入独测中 |
| 独测中 | 固定版本、独立性和测试资源已核对 | 失败按分类回流；通过后先做交付必要性判定，再进入待交付、待用户验收或已完成 |

| 修复中 | 已成功认领Bug并获得所需资源 | 复现、根因、修复、自测及报告齐全后进入待复测 |
| 待复测 | 修复交付齐全，等待独立验证 | 合格测试AI认领后进入复测中 |

| 待用户验收 | 技术验证与必要运行复核齐全，等待用户明确验收 | 用户明确接受绑定范围/版本且关闭条件齐全后进入已完成。仍缺真实交付动作时不得冒称关闭；当前workflow不支持从本状态直接跳待交付，需按已批准的合法流程登记后续动作。未回复不是通过 |
| 已完成 | 必需验证、资源释放和关闭记录齐全，已取得所需用户验收或有效的低风险自动闭环授权；真实交付要求满足 | 保留功能与历史；任务完成不等于允许集成或正式发布，Git额外门禁只认Git专项规则；后续Bug另立关联任务 |
| 阻断 | 环境、授权、未知结果、资源归属等无法继续 | 记录阻断类别及恢复目标阶段；条件核实解除后继续 |
| HOLD | 用户明确暂停/后续排期 | 不自动认领；用户明确恢复后核对依赖与断点 |
| 已取消 | 用户取消或按其明确决定取消任务 | 保留原因、证据和资源释放记录，不等于已完成 |

表中“自测齐全”指最新相关代码修改之后的实际命令、结果、固定版本/文件指纹和未测项；旧自测或修改前结果不得充当当前交接证据。

### 3.0.1 阶段与计划角色强绑定（硬规则）

任务阶段与 `plannedRole` 不是两个可独立漂移的字段。任何阶段流转都必须同时校验并写入与该阶段匹配的计划角色；**只改 `status` 不改 `plannedRole`，或反过来，只要形成阶段/角色不一致，就属于非法流转**。

强绑定关系如下：

- `待准备` / `待开发` / `开发中` / `测试失败待修复` / `修复中`：`plannedRole=开发AI`
- `待独测` / `独测中` / `待复测` / `复测中`：`plannedRole=独立测试AI`
- `待确认`：`plannedRole=用户`
- `HOLD` / `已取消` / `已完成`：默认 `plannedRole` 为空，除非专项规则明确要求保留观察角色
- `待交付` / `交付中`：按已登记的真实交付动作执行者设置角色，不得默认写开发AI
- `待用户验收`：`plannedRole=用户`
- `阻断`：按 `resumeTarget` 对应的下一责任角色记录；若恢复目标未明确，`plannedRole` 为空，不得猜测

以下为必须原子完成的角色交接：

1. 开发完成：`开发中 → 待独测` 时，必须在同一次受控流转中写 `plannedRole=独立测试AI`，并清空开发侧 `assignee/sessionWindowName/sessionId`。
2. 修复完成：`修复中 → 待复测` 时，必须在同一次受控流转中写 `plannedRole=独立测试AI`，并清空开发侧占用。
3. 测试失败：`独测中/复测中 → 测试失败待修复` 时，必须同步写 `plannedRole=开发AI`，并清空测试侧占用。
4. 证据不足：测试阶段回 `待准备` 时，必须同步写 `plannedRole=开发AI`，不得保留独立测试AI角色。
5. 技术通过且无真实交付动作：进入 `待用户验收` 时必须写 `plannedRole=用户`，不得继续挂开发AI或测试AI。

发现历史数据存在如 `待独测 + 开发AI`、`待复测 + 开发AI`、`测试失败待修复 + 独立测试AI` 等非法组合时：**任何AI都不得继续 claim 或靠自身角色解释绕过**；必须先通过看板受控治理入口把阶段/角色修正为一致状态，并保留修正事件。

“独测通过”是验证结论，不另建任务阶段；旧的待测试/待独立测试映射到待独测，测试通过待用户验收映射到待用户验收。旧待调度审核先核对交付证据，不能批量改成通过。已移交是责任变更事件，不覆盖原任务阶段。排队是资源状态，不能把已实现功能改成待开发。

### 3.1 独测/复测通过后的交付必要性判定

技术通过后**不得默认生成开发AI交付任务**。报告必须记录：是否存在非空真实交付动作、动作执行者、目标环境/版本、是否需要人工验收、是否有明确自动闭环授权。

- 有已授权真实动作：按受控状态机进入待交付/交付中；动作与任务范围必须匹配。
- 无真实动作但需要人工验收：直接进入待用户验收，通知具体入口、步骤和通过标准。
- 无真实动作且用户明确授权该类低风险任务自动闭环：完成关闭证据和资源释放后进入已完成，不伪造人工验收。
- Git项目严格区分任务分支、发布集成线、正式发布候选和main，全部门禁只引用Git专项规则。集中验收延期可以不阻断满足技术门禁的发布集成，但绝不等于已验收或允许正式发布；不得借此扩大真实生产写入、付费、迁移、部署授权。
- UI/用户可见交互、高风险变更或用户指定亲验的范围，必须保留明确人工验收记录；不得用技术通过替代。

“交付”不是继续开发的别名。交付阶段禁止新增功能、顺手修复未登记问题、重构或改写已通过测试的业务逻辑；若交付动作导致被测代码、依赖、配置语义或运行行为发生实质变化，原独测证据对受影响范围失效，必须回到待复测/待准备，而不是继续强行交付。

### 3.1.1 Git 提交 / 推送门禁

Git动作只按 `docs/governance/Git与工作空间协作规则.md` 执行，其他文档不复制另一套时序。非Git项目以文件指纹和配置快照固定被测范围，不伪造提交。需要人工验收时使用 `taskctl need-user --project ...` 或等价通知，明确任务、版本、入口、最少步骤和通过标准；“继续”“可以”、沉默或技术通过不等于用户接受。

## 4. 正常交接与修复闭环

普通流程：需求确认/准备 → 按角色和就绪门禁claim → 开发中（自测及固定版本）→ 待独测 → 独测中 → 交付必要性与人工验收判定。修复流程使用待复测/复测中。Git集成与发布在独立证据中记录，按Git专项规则执行，不能靠改任务阶段代替。

上述每一次跨角色流转都必须遵守“阶段与计划角色强绑定”：进入开发阶段即切开发AI，进入独测/复测阶段即切独立测试AI，进入待用户验收即切用户；不得先改阶段、稍后再补角色。

修复流程：独测中/复测中 → 测试失败待修复 → 修复中 → 待复测 → 复测中；通过后同样先做交付必要性判定，不再一律回待交付；失败保留旧报告进入下一轮。开发只能声明实现和自测事实，不能为自己登记独测通过。

用户在 **待独测 / 待复测** 阶段可以直接从看板打回，不需要先等测试AI认领。打回原因映射仍按统一规则执行：原需求缺陷 → 测试失败待修复；证据/固定版本/准备不足 → 待准备；需要用户重新决定规则 → 待确认；暂停 → HOLD。打回同时同步计划角色：测试失败待修复/待准备 → 开发AI，待确认 → 用户，HOLD → 空。该动作是用户审阅决策，必须记录 user_reject 和真实状态变化。

开发报告与测试报告写入各自唯一文件，再更新任务摘要。交接不依赖即时聊天消息送达：消息失败时记录报告路径与接收状态，接手者主动读已有报告，不因通信故障重复实现或重发业务请求。未收到成功工具回执不得声称任务已认领或对方已执行。

角色完成本任务交接并释放资源后，应继续扫描**本角色**可执行队列，而不是把“已交给下一角色”理解为当前会话必须结束。开发AI在待独测/待复测交接后重新扫描开发候选；测试AI在测试结论落盘并释放后重新扫描测试候选。新的正式认领仍须重新执行guard、所有权和资源核对，不继承上一任务的执行权。

技术审查由**未修改过被测任务代码**的测试AI结合需求、差异、测试证据执行，自动检查作为辅助；不能只照开发AI的实现描述当验收标准。测试AI此前写过测试报告、断点、治理文档或审计记录，不因此失去独立性；是否独立只看是否实际改过代码。跨端合同变化须两端任务记录同一版本。

## 5. 失败分类与停止条件

| 分类 | 处理 |
| --- | --- |
| 已确认需求内代码缺陷 | 完整报告进入测试失败待修复；保留Bug编号与父功能关系 |
| 报告/固定版本缺失 | 待准备，要求补证据，不冒充代码失败 |
| 环境、凭据、工具能力或授权不足 | 阻断，标明未测项，不盲改业务实现 |
| 规则矛盾、新需求或业务取舍 | 待确认，列选项，不降低测试预期让其通过 |
| 偶发或结果未知 | 保留原始证据先核查；有副作用请求先查询再决定重试 |

失败报告至少包含步骤、预期、实际、证据、影响范围和最低复测范围；缺项不得自动修复。第二次同一问题修复仍失败，停止同样的猜测式补丁，重新读完整调用链并形成根因分析；可按工具管理规范自主查GitHub。分析确认新证据后再继续，无法确认则阻断，不无限循环。

## 6. 自动认领与资源

只有用户已授权执行的就绪任务才可自动领取。开发领取待开发或测试失败待修复；测试领取待独测或待复测，且测试执行者**没有修改过本任务代码**、权限与前置条件满足。测试报告、测试断点、治理规则、计划、说明文档等纯文档修改不得作为独立性冲突依据。历史负责人可以优先恢复自己的有效任务，但不能越过锁、重复领取或无限保留空占用。

优先排序：严重程度/阻断性优先；同级优先复测和已有缺陷修复；再按入队时间，最后用任务ID稳定排序。资源冲突不能抢占正在执行者。详细认领、整组资源、异常恢复和串行降级见任务认领与资源占用规范。

当前没有覆盖全部实际入口的硬锁证明；在工具核验前，共享写入和浏览器仅由已确认单一执行者串行操作。规范、SHA检查、任务消息、Git工作树均不能冒充全局硬锁。没有已运行执行器时，AI只在启动/恢复/完成任务时检查队列，不声称后台自动唤醒、定时巡检或已创建新AI。

**工具失败不等于业务停止**：若工具明确返回命令未启动、文件未修改、无副作用，属于工具调用/路由错误，任务阶段、执行权和资源状态保持不变，修正调用后继续当前唯一下一动作。只有结果未知、已产生副作用或无法证明未写入时，才按未知结果或阻断流程核查。

### 6.1 受控状态与事件同步

任务当前阶段/优先级/执行归属只以各项目注册表为真值；events记录历史与治理证据，不是第二套当前状态。已接入项目的任务创建、更新、认领与流转走受控 `taskctl`/API/adapter，禁止手工拼接机器表。服务不可用时保留报告、断点及未同步事项并记录失败；不得伪造成功或绕过注册表守卫。紧急安全止损仅按第2.1节边界处理。该协议仍不代表Runner所有写入通道已经不可绕过。

用户对执行中任务发出stop_request后，合规AI在下一次写入/测试前guard；完成断点和资源释放后ack-stop，任务才进入HOLD。仅看板出现stop_request不能证明底层所有写入口已经物理停止。

用户在看板中的 `user_review` 属于任务执行**最高优先级治理输入**，原话必须保留并在页面以红色问题卡显示；`user_accept/user_reject` 属于审阅决策，必须与普通留言分开展示，并显示实际状态变化。合规AI每个执行身份在认领、继续写/测、完成一个小功能准备进入下一步、或进入空闲时，都通过带稳定actor/session的guard获取自己scope内未读留言；存在未读留言时先阅读、按需用 `reply-user` 绑定原问题回复，再 `ack-user`，之后才可继续。一个AI的已读/回复不能替代另一独立测试AI自己的读取。AI需要用户配合时写 `user_action_required`（推荐 `taskctl need-user`），内容必须具体到“需要用户做什么、为什么、完成后任务如何继续”；条件满足后写 `user_action_cleared`。

任务看板面向用户的“本任务负责”必须描述**功能/内容范围和边界**，不能只写R编号、测试通过数、报告路径或“已完成开发”等过程证据；过程证据归“当前进展/历史事件”。任务职责应回答“这个任务实际管哪些功能、明确不管什么”，用户配合应回答“用户现在具体要做什么”；看板卡片和详情使用同一presentation语义。

### 6.1.1 用户反馈分类与权威文档落档

用户在聊天或看板提出的信息不能只读完留在会话/events。执行AI必须先判断性质，再写入**对应权威入口**：

- **BUG / 现有缺陷**：已有计划、既定规则、已实现功能或已承诺验收项没有按要求工作，包括回归失效、显示错误、漏实现。写对应专项计划的“当前缺口/修复边界”（若计划已有同类章节则就地维护），同时在 `报错记录.md` 记录用户现象、根因、修复和验证；需要状态流转时再同步任务总清单/测试报告。
- **新需求 / 范围扩展**：此前计划没有要求的新能力、新交互、新业务规则，先写对应专项开发计划；只有跨多个模块且没有专项计划时才写项目总计划，并明确需要建立/更新哪个专项计划。不得把新需求伪装成BUG，也不得只写报错记录。
- **验收/证据问题**：实现范围未变，只是证据不足、独测未做、固定版本不明，写测试报告、断点和任务状态，不改业务计划正文为“新增需求”。
- **业务决策变化**：用户改变既有规则或优先级，写对应专项计划的决策/边界，同时记录旧规则被新规则取代的时间和影响范围；必要时同步总计划/任务总清单。

落档位置必须依据模块职责和文档索引选择；被管理 ERP 项目中的“BUG反馈系统产品计划”只描述 ERP 内“BUG反馈页面/附件/通知”产品模块，属于**外部项目反例，不是 WyerpTaskboard 本地文件或执行前置**。本项目开发缺陷总账使用 `报错记录.md`。无法确定归属时先读 `docs/文档索引.md` 和相关专项计划，不得为了省事随便追加到当前正在编辑的文档。

### 6.1.2 看板新需求入口与AI拆解

看板中的“新增需求”不是普通任务留言，而是项目级需求入口。第一版采用 cooperative AI intake：

1. 用户提交后，服务必须持久化为“待AI拆解”的需求记录，并在任何合规AI的下一次 guard 中作为高优先级待处理项返回；没有合规AI在线/被调度时只保证排队，不宣称已经后台无人值守拆解。
2. AI开始拆解前先读 `docs/文档索引.md`、任务总清单及可能相关专项计划，判断是否属于已有模块。已有模块必须更新既有专项计划；不存在对应模块时才建立新专项计划，禁止为了方便重复建计划。
3. 拆解出的正式任务必须写入项目任务注册表，包含稳定任务ID、轨道、优先级、阶段、计划角色、职责边界、**主计划**和目标文档；看板从任务总清单自动读取，不另建第二套任务真值。
4. AI对需求存在问题时，在需求线程向用户提问并等待回复；用户补充与AI回复均保留关联关系。需求未澄清前不得擅自猜业务规则并生成“已确认”任务。
5. 需求完成拆解后记录关联计划和新任务ID；后续开发、测试、用户验收继续走正常任务流，而不是长期停留在需求队列。

### 6.1.3 扫描候选与AI消费

候选只用于减少人工发现延迟，**不是任务阶段真值、认领结果、资源租约或独测结论**。当前源码调度模式与已部署运行态分别核验，入口见 `docs/任务看板总计划清单.md`。Windows计划任务是否禁用不能单独证明常驻服务扫描是否停止；不得按历史调度名称推断自动化已启用。

合规AI在启动/恢复/自动任务运行时，如果B-10健康且存在未消费候选，应把候选作为高优先级入口，但正式操作前仍必须：

1. 重读项目任务注册表当前阶段/优先级/角色/负责人；
2. guard用户留言、待拆需求和stop/HOLD；
3. 重新核对断点、交付/修复/测试报告、活动Job及文件/浏览器/测试资源；
4. 测试任务重新核对实际执行者独立性；
5. 候选snapshot/revision已变化时标记stale，不复用旧结论；
6. 只有重新核对仍满足条件时，才用本次真实actor/session执行正式claim。

本机扫描器不得冒充developer_ai/test_ai，不得自行写执行身份、开发中/独测中/复测中、测试结果或用户验收。只有实际启用、获授权且经当前版本现场验证的触发链路才能报告可用；否则只报告已验证的本机发现/手动消费能力，不宣称后台已创建、唤醒或认领AI。

候选消费顺序必须执行“**角色过滤 → 当前阶段可介入性 → stop/留言/负责人/资源guard → 产品阶段 → 轨道与优先级/阻断性 → 正式claim**”。因此开发会话看到正在独测/复测的候选时只能忽略其执行状态，除非该任务已经正式回流成开发可介入阶段；不得为了确认测试做到哪里而主动追踪测试执行。
测试角色在用户授权的连续执行范围内完成交接、释放后检查同角色候选；无合格候选时结束当前执行，不切换开发身份，也不擅自启用任何本机定时任务或后台自动化。
测试失败/阻断正式回流开发时，测试AI为复现保留的临时服务、进程、端口、浏览器会话或夹具必须作为“测试临时资源 / 待开发观察”登记，而不是继续算作test_ai正常执行资源。登记至少包含PID/端口/路径、创建者、用途、接手开发角色、清理条件和证据。developer_ai读取/复现后显式确认是否继续接管；继续使用则重新登记developer_ai owner/session，不再需要则安全清理。孤儿、身份不明、正式资源冲突、持续外部写入或有凭据/真实数据风险时，先保留复现证据再停止/隔离，不能以“等待开发查看”为由长期保留高风险现场。

### 6.1.4 计划审计 / 历史功能盘点的任务化闭环（硬门禁）

任何“计划审计、历史功能盘点、已实现功能补档、遗留缺口清查、文档补全”任务都不能只产出一份说明或表格后结束。**审计结果必须在同一轮被转换成任务注册表中的正式任务，或明确关联到已经存在的正式任务ID。** 看板服务只读取项目任务注册表，不从计划正文自动猜任务；因此执行审计的AI对“结果任务化”负责。

审计任务结束前，对每个发现项必须给出且只给出一个处置结论：`无需任务`、`待确认`、`HOLD`、`待准备`、`待开发`、`待独测`、`待复测`。判定口径如下：

1. **计划要求存在但实现缺失、实现不完整或承诺验收项尚未开发**：建立/关联开发任务；资料齐全进入`待开发`，材料或依赖未齐进入`待准备`，规则仍需用户决定则进入`待确认`。
2. **功能已经实现，但没有可信的独立测试证据**：建立/关联测试任务，进入`待独测`；若固定版本、开发交付、自测证据或测试环境尚不满足测试准入，则先进入`待准备`并把计划角色设为开发AI，补齐后再交独立测试。
3. **功能曾经独测/验收过，但其后相关代码、依赖、接口、数据结构或关键配置发生变化，旧证据已不能覆盖当前版本**：建立/关联`待复测`任务；证据或固定版本不齐时先回`待准备`。仅“以前通过过”“计划里写✅”不能免除复测判定。
4. **缺口只剩真实外部接口、真实账号、真实额度、真实浏览器或其它运行条件验证**：如果实现本身已完成，则按测试任务处理；条件未齐为`待准备`，条件齐全按首次独立验证/修复后验证分别进入`待独测`或`待复测`。不得把“缺真实验证”留成计划正文里的孤立备注。
5. **已有用户授权但明确暂缓的任务**：可登记HOLD。AI自发的可选增强不适用任务化要求，只进入 `AI优化建议与候选需求池.md`，默认待用户查看；不得借审计创建新需求。重复项关联现有任务；无需任务必须说明非缺陷、范围外或已被完整覆盖的依据。

任务化时必须遵守“**先查重，后建新任务**”：同一范围已有任务则更新/关联现有任务，不得为了审计方便重复建任务。新建或关联后的任务必须包含稳定任务ID、父功能、track、优先级、当前阶段、计划角色、职责边界、主计划、关键文件/只读依赖、断点和报告入口。

审计报告/映射表必须额外记录：`处置结论`、`关联任务ID`、`判定依据`。除`无需任务`外，任何发现项如果没有正式任务ID，就视为审计未闭环。**存在未任务化发现项时，审计任务不得进入待独测、待交付或声称完成。**

历史“已完成”功能同样适用本门禁：审计目标如果包含“当前版本是否仍可靠”，就必须核对独测/复测证据是否绑定当前版本；证据缺失、过旧或已被后续代码变更覆盖时，必须生成相应测试任务，而不是沿用历史完成标签。


### 6.1.5 任务看板写入边界（硬红线）

WyerpTaskboard 的定位是**任务治理与协作控制层**，不是被管理项目的业务内容编辑器或第二存储库。看板可以读取项目文档作为任务上下文，但写入权限必须最小化并按职责隔离。

**必读文档的依赖方向固定为：任务看板关联 → 执行AI读取项目原文。** 看板负责在任务治理数据中关联主计划、溯源、只读依赖、目标文档等路径，并在任务详情提供入口；执行AI据此进入对应项目目录读取原始必读文档。项目业务文档不需要、也不应为了被看板管理而反向引用 WyerpTaskboard；看板不得复制这些正文成为第二套必读内容。

**看板服务允许直接写入的范围仅限：**

1. 被管理项目的任务注册表中规定的治理字段，例如任务阶段、优先级、计划角色、负责人、会话信息、准备条件、主计划/报告/断点引用等；
2. 资源台账中的认领、释放、资源占用和恢复信息；
3. 用户审阅、留言、停止/恢复、测试结果、状态变化等治理事件；
4. WyerpTaskboard 自身 `data/` 下的事件日志、事务日志、运行状态和其它治理辅助数据。

**看板服务禁止直接修改：**

- 被管理项目的业务计划正文、产品需求正文、README、必读、报错记录等业务/说明文档；
- 项目源码、测试代码、脚本、数据库结构或真实业务数据；
- 业务配置、环境变量、API Key、Token、账号凭据或其它敏感配置；
- 项目测试报告和任务断点正文，除非未来有单独、明确、受控的专用写回协议并经用户授权。

需要修改上述内容时，必须生成/关联正式任务，由对应项目内的合格开发AI或测试AI进入该项目工作区执行。看板只记录任务ID、状态、关联路径、执行身份和事件，不替执行AI写业务内容。

**禁止双真值：** 看板不得把项目计划、README、源码摘要或数据库内容复制到 WyerpTaskboard 目录后作为新的当前真值。看板自己的事件/缓存只能用于治理、展示和审计；任务阶段的唯一当前真值仍是被管理项目的任务注册表，业务内容真值仍留在被管理项目目录。

### 6.2 疑似失联与异常接管

**能恢复原会话时优先恢复原会话，不做异常接管。** 仅“几分钟没有输出”、窗口暂时无响应或单次Shell超时，都不足以判定允许接管。

B-10把“疑似失联”和“允许异常接管”分成两个独立治理事件：

1. `suspected_disconnect`：只表示发现可能失联；必须记录现场依据，例如原Session是否可恢复、是否仍有active/recovering Job、文件是否继续变化、进程/端口/浏览器/数据库等资源是否仍在使用、断点是否存在。**它不授予接管权。**
2. `takeover_allowed`：允许两个明确入口：①用户在任务看板已认证浏览器点击授权；②用户在**当前对话**明确说允许接管指定任务或指定项目范围，受托AI经实时现场核验后通过已认证的 `taskctl takeover --user-quote ... --evidence ...` 转送此指令并连续执行。第二类必须记录用户授权原话摘录、范围、实际转送AI/Session、疑似失联核验证据；不能根据历史泛化授权、AI自行建议、计时器、仅无输出、无关对话或未经核验的“用户可能同意”生成授权。普通 bearer 未附有效对话授权证据仍拒绝。**聊天转送是可审计的委托声明，不是平台密码学签名；不得声称已验证用户消息签名。**
3. 授权绑定当时的当前负责人、技术Session ID和registry revision；其中任一变化后，旧授权自动失效，必须重新核验/授权。
4. 新执行者使用 `taskctl takeover` 时必须提供新的负责人、会话窗口名称和Session ID；对话授权模式还必须提供 `--user-quote`（用户当前明确原话）和 `--evidence`（实际核查原Session可恢复性、活动Job、未完成操作、资源写入）。CLI 连续记录 suspect、allow、takeover，无须再让用户去看板点击；成功接管只替换执行身份/会话，不改变任务中央阶段。授权后仍不能强抢未停止的旧执行者。
5. takeover事件成功后一次性授权立即消费；用户也可在执行前撤销授权。
6. 异常接管仍是cooperative governance，不代表Runner/WebCodex已经能够物理阻止旧会话继续写。无法证明旧执行已停止副作用时，应保持阻断/等待，而不是强抢资源。

## 7. 进度、证据与长期功能

每个独立小功能/测试组完成立即记录断点，外部操作发出前及结果未知时也记录；恢复先核对执行者、版本、依赖、未决结果，再继续唯一下一动作。只回归受影响范围，不因会话中断从零重复开发。

项目总计划保留全部功能；功能实现与回归清单记录已实现子项、证据与回归入口；待办任务总清单保存当前阶段和下一步；执行台账保存身份及资源；每轮报告保存不可改写的证据。状态的权威位置不能有两套：工具接入前以待办任务总清单的任务行、台账的资源行为准，后续工具接入应明确迁移，不双写两套互相冲突的状态。

## 8. 授权与关闭

浏览器与测试资源只按本地 `docs/governance/任务认领与资源占用规范.md`；测试证据按 `测试报告/README.md`。账号、外部接口、付费、凭据和生产数据必须有当前任务明确授权，不能继承ERP专属文档中的历史授权。外部参考记录来源、版本与许可，不把研究当运行证据。

交付按交付检查与通知规范执行；文档任务只需文档交付及对应检查，不为证明文档完成启动业务服务或数据库。独测未执行必须保留未测试，不将自检当独测。用户验收被否决时，按实际缺陷或新需求分类回流；仅聊天中的“好、继续”而未指明验收范围，不能关闭所有功能。
## 版本发布与执行门禁

- 版本按组件独立管理：修改 WyerpTaskboard 软件代码只升级软件版本；修改 Chat Wake 扩展代码只升级扩展版本。两个组件都发生修改时才各自升级，禁止为了“同步版本号”无意义地给未修改组件加版本。
- 看板源码版本来自 `package.json.version`，运行版本来自实际服务 `/healthz.version`；正式交付须核对目标版本一致。开发中未部署的源码与正式服务可能不同，必须分别注明，不为消除差异擅自重启。自动候选仍须满足其已批准的版本合同。
- Chat Wake 扩展最新版本真值为 `browser-extension/chat-wake/manifest.json.version`，并要求 `config/chat-browser-wake.json.expected_extension_version` 与 manifest 一致。
- 每次自动候选开始前只核对“各自是否最新”：浏览器实际加载的 `extension_version` 必须等于扩展最新版本；`taskboard_version` 由当前看板服务自身 package 版本提供。扩展版本与看板版本允许不同，禁止因为二者数值不同阻断 claim。
