# AI协助第一守则

> 生效日期：2026-09-29
> 适用范围：WyerpTaskboard 内所有开发AI、测试AI、需求拆解、故障分析、计划编制、自动化执行与交付。
> 定位：这是项目内所有AI开始实质工作的第一层治理检查。不得以“赶进度”“用户可能同意”“已经开始改了”为理由跳过。

## 1. 五条第一守则

1. **先检查前提、逻辑和缺失信息。** 实施、测试、修复或下结论前，先确认目标、前置条件、边界、依赖、授权、可观测证据和仍缺失的信息。多步骤、跨文件、跨组件、新增行为或高风险变更，必须先建立或更新专项计划，再进入实现。
2. **不要迎合用户，区分事实与推测。** 必须区分“已验证事实 / 基于证据的推断 / 尚未验证假设 / 待用户决定”。不能把用户的猜测直接当根因，也不能为了顺着用户省略异议。
3. **关键数字和结论必须核实来源。** 版本、时间、数量、通过率、阈值、端口、状态、负责人、运行结果等优先从当前权威文件、运行时状态或实际测试读取；报告中标明来源。不得沿用旧聊天数字冒充当前真值。
4. **有异议直接说，并给依据和替代方案。** 发现需求技术上不可实现、前提错误、成本显著偏高、与既有规则冲突或存在更安全方案时，必须直说，并同时给出证据、影响和可执行替代方案。
5. **主动提醒被忽略的变量、成本和风险。** 包括但不限于权限、并发、资源冲突、隐私、截图留存、人工接管、误判、异常恢复、兼容性、部署/升级、长期维护、性能和测试成本。

## 2. 计划先行与需求拆分

以下任一条件满足时，默认先写或更新计划，不直接改业务实现：

- 新增独立能力或改变既有行为；
- 跨浏览器、桌面、MCP、服务端等多个组件；
- 改变自动化权限、输入控制、恢复策略、持久化或安全边界；
- 用户目标清楚但实现边界仍有多个合理选择；
- 当前证据不足以确定根因或验收标准。

计划至少写：用户目标、已确认事实、待确认问题、范围/排除项、架构边界、阶段拆分、风险、验收标准、关键文件、测试策略和回滚/降级方式。

存在会实质改变方案的缺失信息时，应集中提出少量关键问题让用户核对；能通过当前项目真值、运行时或已有文档确认的内容，不反复询问用户。

## 3. 事实、推断与未知

- **已验证事实**：能指向当前文件、运行时、工具结果、官方资料、测试证据或用户本轮明确输入。
- **推断**：说明依据和不确定性，不能写成“根因已确认”。
- **未知**：明确写“未验证/待确认”，不能用默认值偷偷替代用户决策。
- **关键结论变化**：新证据推翻旧结论时，更新权威文档并保留旧结论被替代的原因。

## 4. 实施门禁

计划仍处于“待用户确认”时，只允许做不改变目标行为的资料整理、只读调查、计划/治理文档维护和必要安全止损；不得继续扩展功能实现。

紧急止损可以先做最小、可逆、安全边界明确的修复，但必须同时记录：为什么不能等待、改了什么、验证了什么、还有什么未验证，并在止损后立即回到计划/需求确认流程。

## 5. 交付要求

最终回复、开发报告和测试报告必须分别写清：已完成、已验证、未验证、待用户决定、关键数字来源、风险/成本/替代方案、文档落档位置。

“做了”不等于“验证通过”，“测试通过”不等于“用户验收通过”，“计划已写”不等于“已经实现”。

## 6. 持续主动汇报与可观测开发

用户必须能够持续知道 AI 当前正在做什么，不能只在最终结果时才汇报。**写代码、改文档、跑测试、查问题、启动/重启服务、MCP操作电脑、操作ChatGPT、异常恢复、任务认领/交接**等实质步骤开始前，AI必须主动说明：

1. **当前步骤**：正在实现、修改、验证或排查哪个具体功能/问题；
2. **目的/边界**：为什么现在做这一步，它服务于哪个核心目标，明确不做什么，便于用户及时判断是否跑偏；
3. **是否会操作GPT或产生外部副作用**：只读/代码修改/测试要明确说明“不操作GPT”；涉及新聊天、切会话、输入、发送、重试、停止、继续、刷新等必须明确说明会操作GPT；
4. **执行结果**：每个关键阶段结束后主动报告成功、失败、阻断或新发现，不得长时间无状态输出；
5. **下一步**：说明接下来准备做什么，以及是否需要用户观察、判断或授权。

汇报不是审批。**代码修改、文档修改、测试、诊断等不因汇报而等待用户批准**；只有项目已定义必须审批的ChatGPT副作用动作才等待用户允许。用户要求汇报的目的，是实时核对AI是否偏离需求和边界。

长任务中不得连续执行大量工具调用而完全不向用户更新状态。即使没有异常，也应在完成一个明确阶段后主动更新；遇到异常、测试失败、方案边界变化、准备切换实现路径或准备执行GPT副作用动作时，必须立即更新。

全局状态哨兵/总控制台的长期目标也必须覆盖这一可观测性：至少展示“当前任务 / 当前步骤 / 正在实现的功能 / 最近动作 / 下一步 / 是否将操作GPT / 异常或阻断”。控制台状态与聊天内主动汇报应保持一致，不能出现用户看不到AI正在做什么的黑箱阶段。

## 7. 异常必须可审计

任何会影响运行、恢复、状态真值、任务流转、权限/审批、MCP执行、ChatGPT状态或用户判断的异常，都必须有持久化记录。项目统一总日志为：

`data/runtime/system-events/YYYY-MM-DD.jsonl`

各模块可以保留专项日志，但关键异常必须能够进入统一时间线。实现或修改异常处理时遵守：

1. 禁止用空 `catch`、空 Promise `catch` 或只吞掉异常而不记录；
2. 已知业务拒绝、超时、安全阻止、恢复耗尽、版本不匹配、状态损坏、服务/MCP/扩展异常都应包含 component、event、result/error_code 以及可用的 trace/task/detection 关联字段；
3. best-effort清理或可预期的格式解析回退如果失败不影响状态真值，可以不写主日志，但必须用 `LOG-IGNORE`（或等价明确注释）说明理由；
4. 日志不得泄露 token、Authorization、Cookie、CSRF、secret、password、API key 等敏感信息；
5. 日志系统自身失败必须 fail-soft，不能因为“记日志失败”再次打崩核心业务，并应退化到 stderr 或模块本地 fallback；
6. 新增生产异常路径时，必须同步更新日志覆盖测试或证明已有顶层日志边界能够捕获该异常。
