## 1. 权威记录与能力边界

待办任务总清单记录任务阶段与准备条件；任务执行与资源占用台账记录原领取人、当前负责人、实际完成人及资源；断点、报告保存执行证据。这些文档不是天然原子数据库或文件硬锁。

优先复用实际工具的持久任务/原子执行认领，再核验文件、浏览器和环境互斥。任务认领不等于文件许可，读会话消息不等于资源占有，文件SHA一致不等于没有其它执行者。硬锁未覆盖所有实际入口时，只允许已明确确认的单一执行者串行写入/操作；无法确认就阻断，不凭空白台账抢占。

确定性工具是否实现、是否覆盖Shell直接写入和旧进程恢复，必须单独验证。本规范不声称已实现自动唤醒或强制排队服务；资源已排队但没有执行器时，在下次启动/恢复/完成任务时检查，不承诺后台继续。

## 2. 任务认领

任务、功能、Bug、测试轮次与执行尝试分别有稳定ID。所有权至少记录任务ID、原领取人ID、当前执行者ID、会话/尝试ID、实际主机/工作区、领取/最后确认时间（含时区）、准备条件、文件组和运行资源、报告/断点。Git 项目还必须记录 `workspace_path / git_available / git_branch / base_branch / worktree_isolated / head_commit`（能取得时）；模型名不能替代唯一执行者ID。

只认领已授权且准备齐全的任务；领取条件与优先顺序引用中央流转规范。并发工具必须一次完成检查与认领，并返回执行身份/代次；同时申请只能一个成功。重复请求沿用同一请求标识，未知结果先查询，不创建第二个任务。

**执行权前置顺序不可颠倒：任务必须先存在于项目任务注册表，才能进入guard/claim；claim成功之前不得修改该任务的业务代码、测试代码、可执行脚本或其它运行行为文件。** 候选发现、需求队列、聊天授权、计划正文、旧断点都不授予写入权。创建任务注册表条目及其最小计划/边界属于治理登记，不等于已取得开发执行权；登记完成后仍必须按认领前汇报与实时占用规则正式claim。发现“先写后领”时不得继续扩写，先登记治理纠正事件并恢复到正常认领流程。

**角色匹配是认领前置门禁，不是排序权重。** 先过滤任务 `计划角色` 与当前执行角色是否匹配，并确认当前阶段允许该角色介入；不匹配的任务直接排除，不参与P0/P1、轨道或阻断性排序。开发AI只能把独测/复测报告当修复输入，不能因测试任务优先级高而认领、跟踪或占用其资源。

**独立测试认领门禁只看代码修改历史。** 对 `待独测/待复测` 的测试AI claim，只有当前测试执行者（actor 或其实际开发会话）曾修改过该任务代码时，才构成 `INDEPENDENT_TEST_CONFLICT`。测试报告、测试断点、缺陷记录、审计报告、治理规则、计划、说明文档以及其它纯文档 `doc_change` 一律不算参与实现/修复，不得阻止原测试AI在开发修复后继续复测。这里的“改过代码”包括业务源码、测试源码、可执行脚本及其它会改变运行行为的代码；单纯文档修改不算。若同时存在真实开发代码修改记录和测试文档记录，真实代码修改仍然构成冲突，不能被文档记录覆盖或洗掉。

**待准备认领**：只引用中央协作规范的状态—角色—认领表。已完成的 WTB-QUEUE-002 允许 `待准备 + 开发AI` 在范围已授权、计划写文件明确且全部实时门禁通过时受控claim进入开发中，以补齐本任务准备/证据；不得恢复“必须先手工改待开发”的旧死路。资料缺口不授权猜测需求、越过依赖或修改范围外代码。

工具未实现时先由明确单一写入者核对并串行登记，其他执行者等待确认。不能多个AI各自“先读后写名字”就宣称原子认领。有人在做时不得因角色或会话变化重领同一目标。

B-10-AUTO的本机巡检候选同样**不授予执行权或资源权**：候选存在不等于任务已认领，也不保留文件、浏览器、测试服务、数据库或会话资源。真正执行者必须在claim前按当前快照重新核对所有权、资源和副作用；候选过期、registry revision变化、出现新负责人/Job/留言/stop时必须作废或阻断，不能凭10分钟前的扫描结果抢占。

### 2.1 认领前实时占用与用户可见汇报门禁

认领不是“看到任务就开始做”。任何开发AI、测试AI或交付执行者在发出正式 `claim` 前，必须重新读取最新任务快照、guard、负责人/Session和可观测运行占用，不能只依赖旧聊天、旧候选或文档里几分钟前的状态。

以下任一条件成立时，任务一律视为**已占用**，禁止另一个AI重复认领或覆盖负责人：

- 当前阶段属于执行进行态：`开发中`、`修复中`、`独测中`、`复测中`、`交付中`；
- 当前负责人或技术会话/尝试ID非空；
- 运行时仍存在与该任务关联的活动Job、受控资源占用或尚未完成的接管/失联处置，且无法证明旧执行者已安全退出。

已有占用只能通过正常完成/释放、明确交接或受控异常接管流程解除；不得用新会话直接覆盖旧owner/session。候选扫描层和最终 `claim` 接口都必须执行这一规则，不能只在候选层挡一次、再允许手工CLI/API绕过。

**用户可见汇报是认领前必做动作。** AI在当前聊天里必须先向用户说明：①任务ID；②任务名称或主要内容；③当前阶段以及为什么此刻满足认领条件；④本轮明确要做什么、不做什么。这样用户可以及时发现接错任务。该汇报默认不是审批门禁，用户没有要求暂停/纠正时可继续认领；如果用户在认领前指出“有人在做 / 接错了 / 先别做”等纠正，必须停止claim并重新读取实时状态。

若claim因已占用、版本变化、资源冲突或其它门禁失败，AI必须把真实阻断原因报给用户，不得把自己当作已认领成功继续写代码。


## 3. 文件组

### 3.0 工作空间隔离

- Git 项目的活动开发 / 修复任务原则上一任务一独立 worktree；两个活动开发任务不得共享同一可写 `workspace_path`。
- 测试AI对被测实现保持只读；测试绑定开发已 push 的固定提交 SHA，版本变化即按影响范围失效重测。
- P1-P3 / 发布候选工作空间只做整合、运行和测试，发现 BUG 后必须转独立 fix worktree，不直接在候选工作区修。
- worktree 规则、候选整合和 main 发布只认 `docs/governance/Git与工作空间协作规则.md`。

只读依赖与计划写入文件分别列出。只读本身不占写锁；正式测试所读对象仍须是固定快照，读取进行中的代码不能给出稳定版本测试结论。

计划写文件使用规范项目/工作区身份和归一化相对路径，Windows大小写、分隔符、别名/符号链接指向同一实际文件时不能绕过占用；重命名同时占旧路径和新路径，生成器、格式化、删除、覆盖也算写。公共文件采用整文件独占，不让两个AI分别改同一文件的不同段落。

多文件任务一次申请整组最小必要资源：任一冲突就不取得部分锁，登记等待原因。不得锁整个项目来掩盖范围不清。公共台账和索引采用短时间串行更新，不贯穿整个业务任务占用；业务文件按实际执行阶段持有，避免所有任务被一份总清单串行化。

运行中需要增加写文件时，停止对新文件的写入并重新检查完整资源组。工具能原子扩展且无冲突才继续；否则先保存断点、确认无未决写入，释放原组后按新组重新排队。不得占X等Y同时让另一个任务占Y等X。无法安全停止的操作保持阻断并说明原因，不强制覆盖。

## 4. 写入和版本守卫

每次实际写入前确认当前任务仍拥有有效执行权及对应资源，并核对读后未改变的文件版本/SHA。版本变化先重读差异，不能关闭匹配守卫、切换宽松匹配、整篇覆盖或恢复别人的修改。

工具层参数错误、命令路由错误或调用前安全检查若明确证明命令未启动且文件未改，不视为任务失败、资源释放或状态回退；修正工具调用后继续。只有工具已启动但结果未知、存在潜在外部副作用或无法证明未写入时，才按未知结果/阻断流程核查。

强制方案必须覆盖实际修改通道；若任意Shell或旧进程仍可绕过，就只能报告约定登记，不能报告硬锁。队列并发1、Git独立工作树或Git提交检查都不自动拦截磁盘文件写入。

## 5. 运行资源

除文件外，根据任务申请：共享服务切换、测试数据库、公共测试账号、浏览器、扩展重载、数据库迁移、交付链和通知发送资源。测试期间其它任务不能改变同一运行对象、账号权限或Schema。

**外部接口额度也是共享消耗资源，但不是默认禁用资源。** 开发自测与测试AI均可在当前任务授权范围内使用真实接口测试数据；认领/执行前应核对对应平台、Key/账号、当前剩余额度或项目安全预算、限流/熔断状态，以及是否已有其它任务正在消耗同一额度。默认采用最小请求数、低频串行；不得多个AI同时对同一Key/账号做高频真实测试，也不得为复现同一已留证问题重复烧额度。若项目已规定日/月预算或单次测试上限，以更严格者为准；需要临时越过软件内部安全预算时必须有用户针对该次测试的明确授权，并在测试后恢复原值。出现限流/封禁/额度异常时立即停止继续消耗，并把实际消耗与恢复情况写入报告/断点。

当前政策上限保持实际任务2、本机重任务1、候选交付链1；不是硬件测量或硬锁实现证明。浏览器交互按真实主机独占1个AI，跨工具/窗口/Profile/无头进程不得绕过；记录操作者、用途、起止和接管状态，结束只释放自己创建或获授权的资源。涉及GPT动作追加全局哨兵专项计划门禁，不依赖外部项目同名规范。改变并发上限须实测并由用户确认。

迁移号先读当前迁移文件和目标库状态再占用，不能把历史台账“060/061”当永久事实；同号唯一负责人，执行前备份，执行后记录文件、时间、验证和恢复证据。文档任务不检查或操作数据库。

## 6. 排队、释放和异常

等待表记录请求时间、任务、执行者、资源组、原占用任务、原因和状态。资源空闲后按严重程度/阻断性、同级复测/修复、入队时间、任务ID排序，只向一个符合全部条件的任务授予同一排他资源。

前述排序只在**同一合格角色候选集合**内生效。开发任务完成交接并释放资源后，开发AI必须重新扫描开发角色候选；若存在可执行项，应重新guard和claim继续，不把上一任务释放视为整轮执行结束。

**候选集合必须同时满足“阶段匹配 + 计划角色匹配”**。开发候选要求阶段允许开发介入且 `plannedRole=开发AI`；测试候选要求阶段为待独测/待复测且 `plannedRole=独立测试AI`。若二者冲突，该任务不得进入任何角色的可认领排序，必须先走治理修正。资源释放不能替代角色切换，角色切换也不能替代资源释放。

测试AI完成并释放资源后，在用户授权的连续执行范围内检查同角色候选；没有合格测试候选时不得切换身份认领开发任务。调度模式与开关按主计划索引中的现行实现说明和实时配置核验，不因本条规则擅自启用定时任务或后台执行器。

完成、失败、取消、暂停或正式交接都必须停止本任务**无人负责的持续写入/浏览器脚本**、核对未决结果，然后释放、原子转移，或按“测试现场保留”规则登记为受控待移交资源。

跨角色交接中的“原子转移”至少包含：目标阶段、目标 `plannedRole`、旧负责人/Session 清空、旧角色排他资源释放；任何一项未完成都视为交接未完成，不得向下一角色暴露为可认领任务。**正常通过/完成路径必须在最终回复用户、发送完成通知或把任务登记为“已完成”之前先释放文件写锁和其它排他资源；已完成任务不得继续出现在“当前文件写锁”表。** 测试失败/阻断回流开发时，为复现而保留的本任务临时服务/进程可以暂不释放，但必须明确标注“测试临时资源/待开发观察”，登记PID/端口/路径、owner、用途、接手者、清理条件和安全状态；不能先释放再暗中把锁送给指定后来者，也不能把未登记孤儿进程当作“保留现场”。若工具/台账异常导致资源无法释放或无法证明归属安全，必须登记阻断/待交接并按安全规则留证后清理，不能保留死锁同时宣称完成。

超时/断连不证明旧执行已停止。心跳过期后先核对进程、代次、文件变化和外部结果；已失效执行者应在受控入口被拒绝。无法证明旧操作停止时不自动抢锁，保留阻断，必要时由用户确认异常处理。不得无限等待不存在的调度。

## 7. 记录和收尾

记录字段：原领取人、当前负责人、实际完成人、独测人分别保存；日期时间到秒并标时区，机器返回异常时间同时标观察来源，不改钟或猜时间。历史责任不明写历史未记录。

开发/测试各自维护唯一报告与断点。资源释放事实不等于任务验收通过；任务阶段按中央规范，验证结果和用户接受单独保留。最终报告必须注明本任务资源是否已经释放或原子移交、等待者、未决结果、完成证据和下一步；只释放本任务记录，不能把整张台账清空后宣布全局空闲。后续AI恢复任何任务时先检查上一次是否留下残余锁；确认任务已结束且无活动执行者时按异常恢复流程清理本任务陈旧占用，并保留接管/释放证据。
