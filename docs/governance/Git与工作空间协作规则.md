# Git与工作空间协作规则

> 生效时间：2026-10-07  
> 适用范围：WyerpTaskboard 自身及其管理的所有 Git 项目。  
> 唯一真源：跨项目 Git / worktree / 分支 / 提交 / 推送 / 候选整合 / main 发布流程只在本文件维护。被管理项目只保留项目级补充，不复制第二套通用规则。
> 规则替代：旧 WTB-GIT-USER-ACCEPTANCE-001 中“用户验收前禁止任务分支commit/push”的口径已由本文件第5节替代；不得按旧任务描述回退本规则。本文中的ERP分支和业务路径是该项目示例，不是WyerpTaskboard自身依赖。

## 1. 核心定义

- **开发分支**负责修改代码。
- **独立 worktree / 工作空间**负责隔离不同活动任务。
- **发布集成线（release integration）**接收满足技术门禁的任务提交，用于整体验证和集中人工验收；不等于正式发布候选。
- **正式发布候选（formal release candidate）**只有满足完整测试、必要人工验收等发布门禁后才能推进。ERP 的 `codex/p1-p3-candidate`（P1-P3）是此类目标，不是日常开发分支。
- **main**只保存已经通过发布门禁、可以正式部署的稳定代码。
- Git merge 成功只证明文件层面可合并，不代表数据库、接口、CSS、运行时或业务逻辑正确。

## 2. 开工前必须明确工作空间与分支

Git 项目的开发、修复、测试、交付任务在开始前必须记录：

- 任务 ID；
- `workspace_path`：绝对工作空间路径；
- `git_available`：是 / 否；
- `git_branch`：当前分支；非 Git 项目写“不适用”；
- `base_branch`：任务从哪个分支 / 提交开始；
- `worktree_isolated`：是否独立 worktree；
- 当前工作区是否存在未提交修改；
- 是否存在其它活动任务使用同一路径；
- 当前 HEAD / 固定提交（能取得时记录）。

开发 AI 接任务的用户可见汇报必须包含任务 ID、主要内容、工作空间、分支、基线和是否独立 worktree。无法确认这些信息时先只读核对，不直接修改代码。

### 2.1 每次开发前必须进行本地—远端版本对齐（2026-10-12 用户确认）

**这是每个 Git 项目每次新开发/修复任务开工前的强制前置门禁**，不是首次进入项目时才执行，也不能用上次聊天中的 SHA 或测试结果替代。先完成下面的核查与可授权同步，再 claim / 修改业务源码：

1. 读取项目最新用户需求、看板任务状态、已确定的唯一 Release 与候选分支，以及现有工作空间的写入者/锁/未提交修改；核对已废弃的能力不得因使用旧分支而被恢复。
2. 在目标项目查询当前工作区绝对路径、所在分支、HEAD、upstream、`git status --porcelain`、独立 worktree 和现有占用；通过 `git fetch origin` / `git ls-remote` 核对实际远端 SHA、ahead/behind 与是否分叉。需要时同时核对受影响任务分支、当前发布集成分支和正式发布候选；**每条分支只与自己的远端跟踪分支比较**，不得要求不同用途的所有分支指向相同 SHA。
3. 对**已获授权、无其他写入者、工作区干净、无分叉**的目标本地跟踪分支，若远端领先且只需快进，执行 `git pull --ff-only`（或等价的已核准 fast-forward），再检查 `HEAD = origin/<当前分支>` 和工作区 clean。若本地领先且提交符合任务来源/最后一次修改后的自测/可提交门禁，先在**原任务分支**完成 commit、push，再读回远端 SHA；不得将未经独测的任务直接推到 Release / main。对新任务，从已经确认并同步的**合法最新基线**创建独立 worktree，不得随意选过期来源。
4. 发现 dirty、未归属文件、分叉、远端变动、活动 AI 占用、缺失远端或无法 fetch 时，**只读盘点并报告具体文件/提交/差异与处理建议**；不得 reset、clean、stash、强制切分支、强推、覆盖他人文件或将不明修改整批提交。使用干净的合法基线独立工作区继续无冲突任务；无法安全对齐的项目/分支应明确标为“未对齐/阻断”，禁止虚报一致。
5. 在**第一次代码修改前**向用户汇报：任务 ID、绝对工作区、角色、源分支与合法基线、HEAD/upstream/远端 SHA、工作区修改状态、对齐动作及结果、是否可进入实施。未完成核对不得先修改后补报。

**每次开发完成后的同一要求：**最后一次相关修改后实际自测通过且任务范围可验证的代码，及时只提交本任务文件、按任务 ID 写 commit 并 push 到其 feature/fix 分支；读回 `origin/<分支>` SHA、核对本地 HEAD 与远端一致且工作区 clean，写入看板证据。若未推送、远端拒绝、存在未提交状态或远端发生漂移，必须显式报告未完成，不得称“代码仓库与本地一致”。独立 QA、CI、可信发布门禁、Release 集成和本机运行服务更新仍分别执行原规则；**提交推送、快进本地、合入正式 Release、部署重启是四种不同的动作**，不能相互替代。

非 Git 项目先核对工作目录、文件归属和 SHA-256 指纹；保留原项目非 Git 事实，不能虚构 commit/push。对已运行服务，还应验证它使用的实际代码目录与经许可更新的 Git 工作区一致；需要服务切换时按独立发布授权和安全重启流程办理，单纯本地拉取并不代表已部署。

## 3. 一任务一可写工作空间

1. 每个活动开发任务、BUG 修复任务原则上使用独立 Git worktree。
2. 两个活动开发任务不得共享同一个可写工作空间。
3. 多 AI 并行时，同一路径只能有一个写入者；测试 AI 对被测实现保持只读。
4. 发现同一路径已有另一活动任务、未知未提交修改或来源不明文件时，禁止覆盖、重置、清理、stash、强制切分支或替别人提交。
5. Git worktree 只能降低“分支互相切换 / 未提交修改互相污染”的风险，不能代替任务 claim、文件锁、浏览器、数据库和服务资源规则。

## 4. 分支规则

- 新功能：`feature/<任务ID>-<简短名称>`
- BUG 修复：`fix/<BUG任务ID>-<简短名称>`
- 线上紧急修复：`hotfix/<BUG任务ID>-<简短名称>`
- 发布候选：使用各项目明确指定的候选分支；ERP 当前为 `codex/p1-p3-candidate`
- 稳定发布：`main` 或项目明确指定的稳定发布分支

任务按“功能 / 需求 / BUG 边界”拆分，不按目录机械拆分。一个任务可以同时修改前端、后端、数据库迁移、CSS 和测试，只要这些修改共同完成同一已确认任务。

## 5. 提交与推送分层门禁

### 5.1 开发阶段

开发完成一个可验证任务并且**最后一次相关代码变更之后的开发自测通过**后，允许且应及时：

```text
commit
→ push 到当前 feature / fix 任务分支
```

目的：

- 固定可测试版本；
- 避免大量完成代码长期只存在本机脏工作区；
- 让独立测试绑定明确提交；
- 防止多任务混在同一未提交工作区。

开发分支的 commit / push **不等于用户验收、不等于发布、不等于允许进入候选分支**。

禁止：

- 自测失败仍正式提交为“完成”；
- 把多个无关任务放进同一提交；
- 把其它任务的修改一起暂存 / 推送；
- 用“修复一些问题”“更新”“临时”等无法追踪任务的提交说明。

提交信息必须能关联任务，例如：

`feat(ERP-COLLECT-001): 完成采集箱重量尺寸展示`

`fix(BUG-ERP-ORDER-001): 修复订单管理样式丢失`

### 5.2 独立测试阶段

独立测试必须绑定明确的任务分支和固定提交 SHA。测试期间若被测代码再次修改：

- 原测试对受影响范围立即失效；
- 开发重新自测、commit、push；
- 测试 AI 改为测试新的提交。

测试 AI不得为了继续测试而直接修改被测业务代码。

### 5.3 人工验收统一延期到发布集成线基本收口之后

发布收口阶段采用：

`先收版本 → 后集中人工验收`

需要用户人工验收的 UI、布局、交互、显示效果，以及其它用户明确要求亲自查看的功能：

- 可以在任务分支完成 commit / push；
- 独立测试通过，并满足“可进入 release integration”技术门禁后，可以进入发布集成线；
- 人工验收统一延期到：**release integration 基本收口 + 全量功能测试完成 + 主要 BUG 修复完成之后**集中进行；
- 延期期间必须真实记录：`人工验收：待后续集中验收`；
- **禁止把“延期人工验收”记录成“用户已验收”或“人工验收通过”。**

人工验收延期只是不阻断当前版本收口，**不代表任务已经满足正式发布门禁**。

## 6. 什么代码允许进入 release integration

当前发布收口阶段，`release integration` 与“正式可发布”必须严格区分。

任务满足以下条件，即可进入当前发布集成线：

1. 任务归属明确；
2. 代码边界明确；
3. 最后代码变更后的开发自测通过；
4. 已 commit + push；
5. 独立测试通过；
6. 依赖完整；
7. 没有来源不明代码；
8. 没有已知阻断该任务本身的 BUG；
9. 不依赖冻结 E 类工作区、stash 或混合来源不明修改。

即使该任务还记录：

`人工验收：待后续集中验收`

也**不阻断进入 release integration**。

但以下情况仍禁止进入 release integration：

- 代码归属不清；
- 混合提交无法安全形成任务级集成单元；
- 发布依赖缺失；
- 依赖本身埋在尚未拆清的跨任务混合提交；
- 依赖冻结脏工作区 / stash；
- 独立测试未通过；
- 存在阻断该任务本身的已知 BUG。

特别规则：

`任务已完成` ≠ `允许集成`

`允许进入 release integration` ≠ `用户已验收`

`允许进入 release integration` ≠ `允许正式发布`

当前 ERP 发布整理继续只在：

`release/p1-p3-integration-20261007`

完成。现阶段不得因为单个小批次通过，就直接修改真正的 `origin/codex/p1-p3-candidate`，更不得进入 `main`。

### 6.1 什么情况下才算“可正式发布”

只有在 release integration 基本收口之后，继续满足至少以下条件，才允许推进正式发布：

1. 集成测试通过；
2. 完整冒烟 / 全量功能测试通过；
3. 发布阻断 BUG 清零；
4. 必要人工验收已经集中完成；
5. migration / Schema 发布验证通过；
6. 干净 clone 验证通过；
7. 发布候选不存在来源不明代码、未解决冲突或未闭合依赖。

正式推进顺序原则上为：

`release integration`
→ `全量测试`
→ `BUG 修复循环`
→ `migration 双路径验证`
→ `集中用户验收`
→ `clean clone`
→ `正式 P1-P3`
→ `main`

## 7. Release integration / 发布候选工作空间规则

候选分支对应工作空间原则上只允许：

- 拉取 / 对齐候选分支；
- 接收已经批准的任务合并；
- 运行服务；
- 集成测试；
- 冒烟测试；
- 专项回归；
- 用户验收；
- 发布前验证。

原则上禁止直接在候选工作空间开发新功能或顺手修 BUG。

候选测试发现问题时：

```text
P1-P3 / 候选发现 BUG
→ 登记 BUG 任务
→ 从最新候选分支创建 fix 分支
→ 创建独立 worktree
→ 修复 + 开发自测
→ commit + push
→ 独立复测
→ 合回候选
→ BUG复测 + 相关回归 + 核心冒烟
```

## 8. 合并冲突处理

出现 merge conflict 时：

- 禁止无脑选择“全部 Current / 全部 Incoming”；
- 先确认冲突两侧分别属于什么任务和业务规则；
- 需要同时保留的逻辑必须正确整合；
- 冲突解决后重新提交；
- 重新执行受影响功能测试。

没有文本冲突也可能出现集成 BUG，例如数据库字段缺失、接口契约不一致、CSS 覆盖、重复组件、重复初始化或共享状态冲突，因此 merge 成功不能代替集成测试。

## 9. 候选合并后的三层测试

### 第一层：启动 / 健康

至少检查：

- 数据库能否连接；
- 服务能否启动；
- migration / Schema 是否报错；
- 主入口是否可访问；
- JS / CSS / 静态资源 / 关键接口初始化是否存在阻断错误。

### 第二层：核心冒烟

按项目核心路径执行最短完整冒烟。ERP 至少覆盖登录、首页、店铺、采集箱、新增 / 编辑商品、在线商品、订单管理、订单统计、会员 / AI豆、子账号、退出 / 再登录。

### 第三层：本批修改专项回归

本轮合入修改了什么，就重点完整回归什么；未受影响模块只做必要冒烟。每修一个小 BUG 不要求立刻跑全部重型测试，但合回候选后至少做 BUG 复测、相关模块回归和核心冒烟。

## 10. 正式发布前干净环境验证

日常任务测试不需要每次重新 clone。

准备从候选进入 `main` 前，应执行一次干净环境验证：

1. 从远端全新 clone；
2. 切换到准备发布的候选提交；
3. 重新安装依赖；
4. 按项目流程初始化 / 迁移数据库；
5. 启动服务；
6. 执行核心冒烟和必要专项验证。

目的是证明发布不依赖旧缓存、历史 `node_modules`、本机未提交文件、临时配置或旧数据库残留。

## 11. 进入 main 的最低门禁

只有同时满足以下条件才允许候选进入稳定发布分支：

- 本次上线任务范围清晰；
- 候选无未解决冲突；
- migration / Schema 验证通过；
- 自动化 / 自测 / 独立测试符合项目要求；
- 候选核心冒烟通过；
- 本批专项回归通过；
- 必要人工验收已经在集中验收阶段完成；
- 没有 P0 / P1 阻断 BUG；
- 干净 clone 发布验证通过。

`main` 禁止作为普通开发工作区。正式上线后发现严重 BUG 使用 `hotfix`，进入 `main` 后同步回候选 / 开发线。

## 12. 非 Git 项目

如果项目本身不是 Git 仓库：

- `git_available=否`；
- `git_branch/base_branch/worktree` 写“不适用”；
- 不伪造分支、commit 或 push 证据；
- 仍然遵守任务 claim、唯一写入者、工作空间路径、文件资源、测试和人工验收规则；
- 若以后初始化 Git，应先建立独立任务并明确初始基线，不得把现有文件静默包装成“已经按 Git 流程管理”。

## 13. 任务看板必须可见的 Git / 工作空间信息

对于 Git 项目的活动任务，看板 / 资源台账至少应能追踪：

- `workspace_path`
- `git_available`
- `git_branch`
- `base_branch`
- `worktree_isolated`
- `head_commit`
- `pushed_commit`
- 是否存在未提交修改
- 是否存在工作空间冲突
- 候选分支 / 发布分支
- 是否允许合入候选
- 需要人工验收：是 / 否
- 人工验收状态
- 集成测试状态
- 是否允许进入 main

如果当前数据结构尚未实现专用字段，先在任务断点 / 资源台账 / 交付报告中使用同名字段保存；后续实现专用字段时不得改变语义。

## 15. 禁止事项

严格禁止：

1. 多个开发 AI 同时写同一工作空间；
2. 不知道当前分支 / 路径就修改 Git 项目；
3. 候选 / P1-P3 一边测试一边直接开发；
4. `main` 直接开发普通任务；
5. 测试 AI 私自修改被测代码；
6. 已完成代码长期只堆在未提交工作区；
7. 多个无关任务混进同一提交；
8. 独测失败仍合入候选；
9. 必要人工验收未完成就推进正式发布候选或 main；按第5.3/6节进入发布集成线不等于正式发布，不解除生产操作授权；
10. 合并冲突直接整块覆盖；
11. 为清空分支强行合入未完成任务；
12. 来源不明时执行 reset / clean / 强制 checkout / stash / 覆盖；
13. 仅因为 merge 成功就认为可以上线；
14. 候选测试发现 BUG 后直接在候选工作区顺手修；
15. 把 feature / fix 分支 push 误写成“已发布”。

## 16. 简化主线

```text
任务
→ 独立 worktree
→ feature / fix 分支
→ 开发 + 自测
→ commit + push 到任务分支
→ 独立测试
→ 满足技术门禁后进入发布集成线
→ 集成测试 / 发现 BUG 则新 fix/worktree 修复并独测后合回
→ 全量测试与 migration 双路径验证（适用时）
→ 集中完成必要用户验收
→ 干净 clone 验证
→ 正式发布候选 / P1-P3
→ main
→ 获授权的正式部署
```

## 17. ERP 内测 Release 独测 PASS 自动整合（2026-10-08 用户批准）

> 本节补充第5、6、7、14、16节；历史口径与用户2026-10-08最新批准冲突时，本节优先。任务看板仍是任务状态、独测身份和证据的权威真源。本节只规定治理合同，不等于运行触发器已经部署/验收。

### 17.1 三层分支与阶段

- **任务分支**：feature/fix/hotfix 或依法登记的独立分支。最新代码变更后开发自测 PASS，即及时只提交本任务内容并 push，固定完整 SHA 进入待独测/待复测；无需等待人工 UI 验收。开发 push/CI PASS 不能触发 Release 合并。
- **统一内测 Release**：`release/p1-p3-integration-20261007`。本规则登记时已知基线 `72711efaf671a4fd582f8db832edf29a52acaab6`，操作时必须重新读取远端 HEAD，不能固定历史基线作当前 HEAD。独测 PASS 且技术门禁满足后，进入唯一串行集成队列受控合入。
- **正式候选 / main**：`codex/p1-p3-candidate` 仍按正式发布候选管理；`main` 仅正式稳定发布。两者**绝不受内测自动合并触发**，仍需集中人工验收、完整发布验证与明确授权。

### 17.2 独测可信触发门禁

1. 看板正式记录唯一任务 ID、项目、开发/独测身份及角色、任务分支、完整被测 SHA、报告和证据 ID、最新开发自测。独测必须由未参与实现的测试 AI 执行，且记录最新有效 PASS，不允许旧 PASS 或测试后代码变化复用。
2. 权限、资金、跨租户、迁移/Schema、API 契约等必测项按风险检查；缺失独测/证据、FAIL/HOLD、阻断 BUG、缺依赖或来源不明代码一律禁止入队。已登记的**非阻断 BUG**和待集中人工 UI 验收不能无限期阻断内测整合，但保持待办，不得记录为已验收。
3. 由可信看板/交付服务以最小权限派发含 task_id、commit_sha、evidence_id、head_branch 的机器事件；事件仅是**证据索引**。集成器必须从受认证的**看板只读 PASS 核验接口**实时查询权威当前状态，严格核验任务、SHA、证据、测试人独立性、范围和阻断项；端点/密钥缺失、证据异常、响应不符即失败关闭。开发分支 push、CI PASS、用户可编辑 PR 标签/正文或自报 PASS 均不能代替独立测试。
4. 触发器应防止重复派发、旧版本重放，并为拒绝、失败和异常保留可审计的任务/证据关联。看板开发者不得借部署事件修改独测真值。

### 17.3 串行合入和复核

- 内测 Release 只有一个集成队列、一个同时写入者；GitHub Actions 设置统一 concurrency group，`cancel-in-progress: false`。任何本机 Release 集成 AI 也必须接受同一个队列的唯一写入治理，不得与云端同时提交。
- 执行时重取远端 Release 和任务分支，验证远端任务分支 HEAD **恰等于独测 SHA** 且当前 Release 是其祖先；不满足则登记当前阻断，按第17.6节建立受控桥接候选并补齐该新SHA必要独测，不得无限无主HOLD。不得使用强推、覆盖其他 AI 代码、`reset`/`clean`/`stash` 或用普通 merge 偷换被测 SHA。
- 在**固定 SHA** 重新执行必要 CI/静态、核心和变更相关技术检查；合入前再实时确认独测有效。失败、网络异常、权限不足、分支竞态或缺失检查均拒绝合并并记录。
- 仅允许非强制 fast-forward push 到 `release/p1-p3-integration-20261007`，然后读回远端 SHA 核对，登记任务 SHA、Release SHA、证据、Actions URL、时间和结果。GitHub job 串行不能替代看板/本机集成队列的物理协调。
- 合入后的集成回归/核心冒烟独立记录；新 BUG 单独登记为 fix 任务、开发自测 commit/push、独测 PASS 后再进 Release，不以无关历史夹具无限阻断已经通过技术门禁的收口工作。

### 17.4 自动化上线与正式发布门禁

- 代码在统一内测 Release ≠ 本机服务加载 ≠ 人工验收通过 ≠ 可进入 `main`。内测收口后仍需全量测试、发布阻断 BUG 清零、必要人工验收、迁移双路径验证、干净 clone 和正式发布授权。
- “自动触发已完成”必须有**真实闭环**验证：看板独测 PASS 可靠派发 → GitHub 收到事件 → 权威 PASS 接口校验 → 固定 SHA 技术检查 → 串行快进合并 → Release SHA 回写。还必须负向验证 FAIL/HOLD、伪造事件、旧 SHA、冲突绝不合并。
- GitHub `repository_dispatch` 工作流只有部署在仓库**默认分支**才能响应；若默认分支未启用、看板尚无可靠派发、远端只读核验接口/机密配置缺失，必须标“**配置/合同已准备，真实自动合并未验收**”。不可为了启动自动化擅自合并业务改动到旧正式候选或 `main`；配置阻断和合规人工降级处理见第17.7节。

### 17.5 ERP 运行目录与原数据目录隔离（2026-10-08 批准）

- **职责分离**：任务看板只记录规则、身份、任务状态、证据、审计及可视化；GitHub 负责提交、分支、技术检查与唯一串行合并；ERP 运行目录负责启动。看板不直接改 ERP 业务源码、数据库、生产数据或替代 Git 合并执行者。
- **代码隔离**：日常开发工作区 `D:\跨境电商\erp-x20` 存在未提交改动，禁止作为统一内测的运行代码源；内测工作区固定 `D:\跨境电商\erp-x20-worktrees\release-p1-p3-integration-20261007`，必须验证分支、干净状态与远端已核验 SHA。
- **保留既有业务数据**：内测启动必须沿用 `D:\跨境电商\erp-x20\本机数据` 的原 PostgreSQL、wyerp.env、credentials/CSRF 密钥、物流与备份目录，不自动创建空库、新密钥或新租户。外部数据根配置必须识别旧 `配置` 目录与 `secrets` 目录的真实配置文件，任一关键项缺失即安全失败。
- **版本和运行分离**：Release 自动合入后应执行独立集成检查，不能因为 Git 已更新便宣称 8765 当前服务已经运行新 SHA。禁止自动打断用户正在使用的 ERP；用户下次主动启动前才在安全退出旧实例后对 Release 执行有界远端检查、非强制快进更新和来源核对。
- **正式生效标准**：实际启动必须同时核对 Release 提交、进程所用代码目录、旧数据目录、服务健康及用户必要可见验收。旧开发目录原启动文件没有被安全改为内测路径之前，不得宣称它能启动最新统一 Release。角色文档与看板应明示“规则就绪、脚本就绪、独测就绪、自动合并就绪、运行切换就绪”分别是什么，缺一不得冒称全部完成。

### 17.6 分叉、版本漂移和整合冲突的必办闭环（2026-10-13 补充）

> 用户已授权独测 PASS 后进入唯一内测 Release 集成队列。分叉不等于可以强推，也不等于可以无限搁置。本节细化第17.3节的“分叉则 HOLD、整理新候选并补独测”；没有实际执行器不得冒称已自动完成。

1. **固定真实入口**：只有最新有效的独立 QA PASS、完整固定 SHA/分支、报告实际 SHA-256、证据 ID、测试人独立性、开发自测、来源和无阻断项均核验后才可受理。仅专项观察 PASS、开发自测 PASS、旧 SHA PASS、FAIL、HOLD 或历史交付记录都不能冒充当前候选获准合并。
2. **逐项判断**：远端 Release 已包含被测 SHA，则核对改动与证据并记录“已包含”，不可重复 cherry-pick；Release 是远端任务分支被测 HEAD 的祖先，才能依据第17.3节做固定 SHA 技术检查和受控 fast-forward。
3. **分叉必须交由唯一集成角色处理**：当任务分支与最新 Release 分叉、任务分支出现未独测的额外提交或多个修复来自不同历史基线时，登记两端完整 SHA、merge-base、ahead/behind、差异与任务来源，并指定唯一集成执行者。由最新已核验的 Release 建立干净独立集成 worktree/桥接候选，按依赖次序只整合已授权、有归属的有效变更；冲突按函数与业务链核对，不整文件盲选、不改旧脏根目录、不 reset/clean/stash/强推、不恢复被用户否决的旧功能。
4. **新 SHA 必须重新验证**：桥接的 cherry-pick、merge、冲突修正或重放若产生新代码 SHA，须记录“原独测 SHA → 来源提交/文件 → 冲突处置 → 新候选 SHA”，在新 SHA 上完成开发自测和相应集成回归，并由未参与实现的独立测试 AI 对新最终 SHA 重新执行按风险确定的必要独测、记录权威 PASS；不能把旧分支的独测 PASS 拼接或转签为新 SHA 的 PASS。
5. **唯一安全合入**：新候选取得完整技术门禁、CI 与新的权威独测证据后，执行时再次 fetch，确认最新 Release 为最终已测候选的祖先，候选远端 HEAD 等于独测 SHA，且唯一串行集成资源归该执行者；仅允许非强制 fast-forward 到唯一内测 Release，读回远端 SHA、记录结果。若 Release 在测试后再次前进或发生竞态，停止本次写入，重新整理差异并补受影响的测试；不得偷换被测对象。
6. **不得无限无主阻断**：每一次不能立即集成都须在原任务或关联集成任务中登记“阻断类型、当前Release SHA、待集成SHA、负责人、下一步、恢复条件、证据入口”；技术 FAIL 回开发、代码改变回独测、外部授权/配置缺失回具体待办。只说“分叉/HOLD”而无实际处理方案，不算交付收口。

### 17.7 自动派发未就绪时的同门禁交付（2026-10-13 补充）

1. **自动优先，状态必须真实**：可信派发与 HTTPS 核验配置完成时，依第17.2—17.4节自动进入唯一队列。工作流文件存在、开发分支推送或 CI PASS 均不能宣称“已自动合并”；须以实际可信事件、权威核验、固定 SHA 检查、受控快进和 Release 回写组成的真实闭环为准。
2. **配置型阻断不等于业务失败**：缺 GitHub 可访问的受限 HTTPS 只读核验地址、Token、默认分支工作流、访问权限或网络时，标注“可信自动集成未启用/交付配置阻断”，明确缺项、配置责任人、验证方法、恢复触发条件和用户需要提供的具体授权；不得伪造旧 PASS、派发事件、关闭验证器或擅自公网暴露看板。
3. **允许同门禁的受控人工通道，不允许手动绕过**：在用户既有的内测集成授权内，由唯一正式取得集成写入资源的执行者，可在自动事件传输不可用时，使用受认证且可审计的**看板本地权威只读查询**实时验证原任务、独立 QA 身份、最新完整被测 SHA、报告文件真实哈希、证据 ID、无阻断与远端状态，并执行同等 CI/权限/安全检查、第17.6节必要桥接和第17.3节唯一串行 fast-forward。该方式**仅替代自动派发传输**；没有可靠的权威查询、独测或必需 CI，就不能靠人工报告、口头“已通过”、GitHub 标签或用户可编辑文档放行。不得将本条视作自行获取生产或正式发布权限。
4. **交付结果分别记账**：至少记录任务及开发 SHA、当前 QA 固定 SHA/报告哈希、最终桥接候选 SHA（如有）、CI 及可信核验结果、Release 变更前后 SHA、执行者/动作、运行中 ERP 实际加载 SHA、用户验收状态。已合并内测 Release 不等于已经重启服务或可以合并 main；不符合条件时必须留下可恢复的明确下一步。
5. **用户禁令优先**：用户永久否决的旧订单自动同步方案、暂缓且未重新授权的需求、来源不明或资金/权限/租户风险不符合门禁的提交，均不得借“补齐落后分支/尽快合并”恢复。规则修订不代表相关自动集成执行器、云端 HTTPS 或凭据已经实际部署。
