# 任务生命周期完整性门禁修复计划

> 任务：WTB-FLOW-INTEGRITY-001
> 优先级：P0
> 用户确认：2026-10-04，要求在 WyerpTaskboard 项目内解决流程问题并执行。
> 范围：只修改任务看板治理/CLI/服务端/测试，不修改任何被管理项目业务代码。

## 1. 问题与已验证事实

2026-10-04 现场复现三类流程完整性缺口：

1. ERP 需求 REQ-20261004-D342ED3A 已被标记为“已拆解”，但记录的任务 UI-PRODUCT-OZON-LINK-T1 实际不存在。RequirementStore 当前只检查 taskIds 非空，不验证任务是否真实存在。
2. taskctl 的项目型命令普遍使用 `args.project || "wyerp-taskboard"`。跨项目调用漏写 `--project erp-x20` 时会静默操作 WyerpTaskboard 自身，现场已经产生一次误建任务并完成治理纠正。
3. 规范要求 claim 前必须向用户汇报任务ID、主要内容、阶段/可认领依据和边界，但当前 claim API 只校验任务状态/身份等，不要求存在可审计的认领前汇报事件。

## 2. 目标

建立任务生命周期硬门禁，使“需求拆解 → 正式任务 → 认领前汇报 → guard → claim → 执行中状态”成为可验证、可审计的唯一正常路径。

## 3. 实施设计

### R1｜需求拆解引用完整性

- “已拆解”必须同时满足计划、任务ID、关键文件非空。
- 服务端必须验证全部 taskIds 在**同一 projectId** 的当前任务注册表中真实存在。
- 任一任务不存在时返回明确错误，需求状态不得变化，必须列出缺失任务ID。
- 校验必须在服务端生效，不能只依赖 CLI。

### R2｜跨项目显式项目门禁

- 对会读取/修改具体任务或需求的 taskctl 命令，默认要求显式 `--project`；至少所有写操作必须强制。
- `help`、`projects` 可不需要项目；`list` 是否保留默认仅限只读兼容，写操作不得静默默认。
- 缺少项目参数时使用明确中文错误，例如“该命令必须显式指定 --project，禁止跨项目静默默认”。
- 更新 help 文案，避免示例继续暗示所有命令都可省略项目。

### R3｜认领前汇报硬门禁

- 新增受控 `preclaim-report` 事件/命令，绑定 projectId、taskId、actorType、actorId、sessionId 和当前任务状态/更新时间。
- claim 前服务端检查同一 actor/session 是否存在与**当前任务状态快照**匹配的有效 preclaim_report。
- 任务状态或更新时间变化后旧汇报自动失效，需要重新汇报。
- 缺失或过期时 claim 返回明确错误并保持任务未认领。
- 事件只证明“执行者已按流程登记认领前汇报”，不虚称系统能读取/验证聊天正文；聊天内真实汇报仍由治理规则要求，事件用于硬顺序与审计。

### R4｜状态与异常审计

- 新门禁失败不修改任务/需求状态。
- 所有新增错误均返回稳定机器码 + 清晰中文 message。
- 已有统一系统异常日志继续负责运行异常；正常业务拒绝不制造 error 洪泛。

## 4. 兼容与排除项

- 不修改 ERP、扫街雷达等被管理项目业务代码。
- 不改变现有任务阶段集合、角色集合、优先级或看板6列映射。
- 不引入新的常驻服务。
- 不把“preclaim_report 事件存在”冒充“用户已经阅读聊天内容”；它只做流程顺序证明。
- 不允许为了兼容旧调用保留跨项目写操作的静默默认。

## 5. 测试矩阵

1. Requirement：
   - 已拆解 + 全部任务存在 → 成功。
   - 已拆解 + 一个/多个任务不存在 → 失败且需求状态不变。
   - taskId 属于其它项目但本项目不存在 → 失败。
2. CLI：
   - 写命令缺 `--project` → 失败且无副作用。
   - 显式项目 → 保持现有行为。
3. Claim：
   - 无 preclaim_report → 拒绝。
   - preclaim_report actor/session 不匹配 → 拒绝。
   - preclaim_report 后任务状态发生变化 → 拒绝旧汇报。
   - 有当前有效汇报 → claim 成功并进入对应执行态。
4. 回归：
   - taskctl 定向测试。
   - Requirement/HTTP/TaskStore 定向测试。
   - npm run check。
   - 用户已明确本任务不涉及无人值守；因此不修改、不执行 `tests/unattended-core.test.mjs`，也不运行会包含该专项的全量 `npm test`。

## 6. 分批实施与自测

- 批次 A：R1 服务端需求引用校验 + 单测，立即自测。
- 批次 B：R2 CLI 显式项目门禁 + taskctl 测试，立即自测。
- 批次 C：R3 preclaim_report 服务端/CLI/claim 门禁 + 测试，立即自测。
- 批次 D：文档/帮助/相关范围回归，确认无人值守专项未被修改/执行，整理开发报告并交独测。

## 7. 回滚与降级

- 每批为独立最小改动，失败时只回滚本批逻辑，不改变历史任务/需求数据。
- 新门禁仅影响后续写操作，不迁移或重写历史事件。
- 若正式服务尚未部署新版本，源码测试与正式运行态必须分别说明，禁止把源码完成冒充正式生效。
