# WyerpTaskboard｜核心功能与分层验收

> 修订：2026-10-07；WTB-DOC-CLEANUP-001。适用WyerpTaskboard，不把被管理项目业务测试混入本项目。
> 本文定义验收，不声明任何用例本轮已执行。历史版本快照和已失效恢复方案已移出当前要求，原证据仍保留在测试报告中。

## 1. 开测门禁

先读本地测试AI规范和 `测试报告/README.md`，固定任务范围、源码指纹/提交、实际服务、配置与扩展版本。核对最新相关代码变更之后的开发自测证据、独立性、账号与资源授权。材料不足回开发准备，不能由测试AI补实现或补开发自测。

任务注册表决定当前阶段；HOLD/阻断不能因为测试文档写了流程就自动恢复。涉及浏览器、Windows-MCP、外部请求或服务切换时必须取得相应执行范围和资源。

## 2. 三层结论分别记录

| 层级 | 核心范围 | 结论边界 |
| --- | --- | --- |
| A 基础任务看板 | R1–R7，任务、用户控制、数据与服务安全 | 可单独验收，不依赖自动化链路已通过 |
| B 独立手工MCP | 显式调用、白名单、会话关闭与自动系统解耦 | 不等于无人值守或GPT自动恢复通过 |
| C 自动化协作闭环 | 异常识别/恢复、候选投递、角色执行与释放 | 必须现场闭环，不能用配置启用或历史ACK替代 |

“项目全部通过”必须覆盖声明交付的全部层级；只验证A层时只能写“基础看板范围通过”，不得写自动化或整个项目已完成。每层任一必测失败/未测都阻断该层总体通过。

## 3. A层：基础看板核心用例

1. 项目/路径：只读已登记项目；不兼容、离线、权限异常按项目隔离；目录、junction/reparse越界及任意路径注入拒绝。看板自身不依赖ERP运行。退出管理只解除注册，不删除磁盘业务文件；活动任务/资源阻断正确。
2. 注册表/事务：机器区按schema读写；列数异常、重复ID、未知状态/角色/track拒绝；revision冲突不覆盖。覆盖registry已写/event未写、commit标记缺失、损坏journal与备份恢复；相同operation_id不重复副作用。
3. 服务/认证：独立loopback会话、Host/Origin/CSRF、体积与路径限制；其他Node、非Node占端口、PID复用与身份未知均不得误杀。真实启停与互不影响测试在授权隔离环境完成。
4. 页面：全部任务默认值、项目选择、固定6列、列内分页、候选徽标、任务详情、计划/报告安全查看、最新留言回复印章、真实角色名。状态机、卡片显示与候选资格分开验证，刷新后保持正确项目与数据。列映射按页面布局规范及关联任务目标验收，不将尚未实现目标改成通过。
5. 生命周期：同项目需求引用完整；写命令缺project拒绝；无汇报/过期汇报/角色或身份不符claim拒绝；用户留言、停止、占用与依赖变化复核；并发claim只有一个成功。
6. 交接：开发→独测、修复→复测、失败→开发、证据不足→开发准备均原子更新阶段/角色/身份。通过后先做真实交付必要性判定，无动作不空转开发；终态不留幽灵占用。
7. 用户控制：留言与AI回复关联、审阅通过/打回、优先级、停止请求→断点/释放→停止确认、明确恢复；疑似失联不是接管授权。

现有测试入口按范围选择 `tests/project-registry.test.mjs`、`tests/markdown-adapter.test.mjs`、`tests/task-store.test.mjs`、`tests/recovery.test.mjs`、`tests/http-server.test.mjs`、`tests/service-control.test.mjs`、`tests/taskctl.test.mjs`、`tests/web-ui-contract.test.mjs`。静态契约/HTTP 200不能代替真实页面操作结果。

## 4. B层：独立手工MCP

按照 `docs/plans/独立手工MCP集成计划.md` 验证显式status/list-tools/call、白名单拒绝、一次调用后进程关闭。调用前后自动扫描、Chat Wake、健康监控及无人值守开关不得被隐式改变。文档整理不实际调用MCP。

## 5. C层P0-A：异常识别与受控恢复

唯一安全合同为 `docs/plans/全局状态哨兵与人工接管开发计划.md`。**扩展/截图只观察、取证和上报；所有改变GPT页面/会话状态的动作由受控MCP执行器完成。**

必须验证以下正反场景：

- stable时保持轻量观察；正常generating为不可切换，不能为了修心跳或赶时延打断。用户正文提及错误词不能误判系统异常。
- processing_delayed持续约3秒二次确认；execution_error持续约1.5秒二次确认。确认只产生受控恢复意图，不授予点击、停止或发送权；手动模式未批准前不得动作。
- recovery在原会话按批准顺序执行重试/继续或停止→继续，记录动作、次数、结果；不能创建平行任务或换task/detection。
- 普通stale、candidate卡住、composer缺失只诊断，不因此刷新。只有明确异常且常规恢复耗尽、证据新鲜时，才允许提出最后手段刷新，并仍受授权/接管门禁。
- MCP不可用、扩展过期、网络异常、审批拒绝、USER_TAKEOVER、未知输入与执行结果未知时安全停止/降级；不无限重试。人工接管只暂停交互自动化，不强停后台工程任务。
- Service Worker重启、断连与执行上下文恢复后必须保持同一task/detection；epoch/lease/ACK竞争不得生成重复认领或幽灵消费者。
- 恢复成功必须有新鲜heartbeat/页面状态与后续任务继续流转的证据，不能只凭“按钮点了”“MCP返回成功”判恢复通过。

每个异常记录：识别原因、诊断依据、实际执行器/授权/动作、恢复后复核。没有实际恢复结果只能报告诊断或阻断，不能宣称自动恢复通过。禁止为了测试主动恢复已暂停自动化或强行制造GPT刷新。

## 6. C层P0-B：发现、投递与正式认领时延

三个指标分别记录，禁止把ACK叫作正式认领：

| 时间点 | 事件 |
| --- | --- |
| T0 | 已授权任务在当前registry/event及依赖条件下正式变为eligible |
| T1 | re-arm |
| T2 | 扫描完成、唯一候选生成 |
| T3 | 正确消费者lease/candidate_started |
| T4 | 当前候选投递确认ACK |
| T5 | AI复核项目、版本、留言、资源、依赖与角色后正式claim成功 |

正常无阻断、目标角色页面stable且已获自动执行授权的路径：`T2-T0 <= 10s`是自动发现目标，`T4-T0 <= 10s`是投递确认目标；正式认领单独报告 `T5-T0`。T5不得冒用T4，必要复核不能为10秒指标省略，异常停顿应说明。

若页面generating、等待人工批准、登录/模型不符或存在资源阻断，记录真实墙钟时延与阻断区间，不混入无阻断样本，也不通过删除等待时间制造通过。恢复到可执行条件后的继续投递另记录起点。

两个消费者竞争只允许一个真实claim；候选过期、任务revision变化、依赖未完成、前次副作用未知必须拒绝旧候选。历史ACK或单次扫描耗时不能证明端到端通过。

## 7. C层P0-C及稳定性

至少真实跑通一轮已授权开发→独测→失败回流/通过→必要交付/用户验收→释放。测试身份不由开发者换名冒充；执行过程中任务变更、留言、停止和资源都可追溯；角色交接后无幽灵owner/session。

再验证服务/扩展重启、版本漂移、断连恢复、候选去重、审批单次消费、日志离线fallback、控制台非阻塞与托盘恢复。源码声明某能力存在不是现场验证。当前调度实现与开关见总计划清单及实时配置，不按已失效的Windows计划任务假设编写通过结论。
